# 回到任务初心：目标达成与全链路审计

审计基准是 2026-10-10 需求澄清、总体设计，以及后续指定的专家 `catalogs/review-2026-10-09/故障事件与可靠性机制收益审核.html`。最新请求优先；旧 V4 严格交付策略保留独立入口与版本，不混成同一指标。

**判断：训练集群的条件设计评估主线已形成可运行、可复核的闭环；“任意产品通用、智能能力充分验证、内部实测达标”的最终目标尚未全部达成。** 不能因为界面有入口、求解器有输出或自动化通过，就宣称所有原始目标完成。

## 本轮从头检查发现的问题

1. 前轮只修改了前端 Agent 摘要，服务端仍读取旧 V4 参数。现由服务端生成 `design.assessment`，界面、MCP 和 Agent 使用同一审核输入；无效草稿保留以供编辑，但不允许正式确认。测试用相互矛盾的 V4/审核参数验证实际同步内容。
2. 审核虽可运行和导出，却与正式六阶段确认断开。现审核和 V4 均可绑定各自的正式流程；前四步用户确认后计算，结果进入待审核，再由用户确认交付。更改审核参数或指标会改变输入版本，旧流程失效；独立试算不能补充冒充正式运行。
3. 原多规模审核共用目标，缺少目标到损失项的对照。现逐规模目标、六项预算、实际损失、差距和工程核查方向在界面与报告一致呈现。参考权重只是设计起点，需用户确认；不能机械换算为组件 FIT。
4. 原组合收益表还不能直接形成可复核建议。现对已选机制子集筛选、按完整成本或均值排序、以独立种子复核固定候选；显式载入候选后重新确认。仍不是任意工程约束下的全局优化。
5. 自定义恢复链中，前序失败、重执行随后成功时漏计前序耗时。已修复并新增确定性回归；模型版本升为 `review-retained-progress.v2`，专家默认链保持复现。
6. 新任务的智谱自定义提供商 ID 与原生连接入口使用的凭据 ID 不一致。现默认使用原生 `zhipuai-coding-plan`，兼容保留旧自定义配置。真实密钥未配置，不能宣称本机或云端的 GLM Authorization 问题已通过实调用验收。

7. 长仿真进度事件引发完整结果读取堆积；现同一时刻仅刷新一次并合并密集进度通知。OpenCode 目录初始化元数据单独采用 20 秒时限，服务健康仍保持 4 秒快速探测；不自动重试创建会话等写操作。
8. 已交付流程仍显示可再次确认的按钮，可能误开新流程；现完成状态禁用重复交付。旧任务恢复时保留原指标入口，避免打开页面就改变旧设计口径。

## 本轮示例的实际结论

外网参考示例运行 `535ef459-4b0c-4e2b-9f96-e49b2f55a8b2`，720 小时，主评估每场景 128 条轨迹，Shapley 每子集 64 条，候选独立复核 256 条。结果文件和自包含 HTML 位于 `artifacts/goal-audit/`，均为公开参考参数，不包含内部数据。

- 万卡默认组合均值 97.8817%，95% 均值区间 97.4470%～98.3163%，低于 99% 目标。
- 对应允许损失 7.200 小时，实际 15.252 小时；其中保存开销 11.792 小时、回滚约 2.828 小时。缺口应落实到策略和参数，不能仅增加轨迹数。
- 筛选建议为静默检测、干净 step、进程恢复和 DP 弹性；独立复核均值 98.2407%，95% 区间 97.9750%～98.5065%，仍低于 99%。平台明确保留“不达标”的结论，不为达标而修改目标。
- 十万卡默认组合均值 95.4578%，95% 区间 94.5471%～96.3686%，在当前模型下采样支持 94.3% 目标。该结论不等于真实系统达标，也不能当作主规模建议组合在十万卡的复核。
- 二十万和五十万卡示例未另设目标，沿用主目标 99%，两者均未达到；这些目标不是从 MTBF 自动推导的。
- 示例正式流程已走完六阶段；桌面和 390px 布局截图已检查，未发现页面脚本错误或整页横向溢出。报告提供明细筛选、打印和输入快照。

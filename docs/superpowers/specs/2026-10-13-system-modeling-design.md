## 1. 目标与已确认需求

以统一 JSON 系统模型连接系统架构、部署、功能流、故障模式、可靠性机制及分析结果。用户可以从任一图定位同一系统对象，查看其参数、故障影响、保护机制、证据及关联运行。支持一张总览和多张分层、分维度子图，不要求把全部信息挤进一张图。

用户已确认：RBD 同时支持按硬件、软件、网络等故障来源，以及中断、性能下降、静默错误等功能影响切换；两类维度可以组合。不同场景使用相同核心模型，以类型字典、模板和有版本的适配器扩展。

本次设计覆盖前端、后端、存储、求解衔接、导入导出、追溯及验证。图形编辑本身不是最终验收终点：必须完成“建立系统 → 填写故障与机制 → 定义成功条件 → 校验 → 计算 → 回图定位 → 冻结导出”。

## 2. 当前基础与缺口

基线：`43bc8b5`。以下为代码核对结果，而非新增能力。

- `apps/web/src/StaticDiagram.tsx` 从 `tree` 生成纵向静态 SVG 布尔结构图；节点最多显示 150 个、深度最多 30；修改结构必须编辑 JSON。
- `packages/solvers/src/static.ts` 支持串联、并联、k/n、AND/OR 和共享事件 ID，使用 BDD 求解。不同事件默认独立，不支持任意相关性。现有限制包括 64 个独立事件、2000 个树节点、深度 100，以及 BDD 资源限制。
- `packages/solvers/src/repairable.ts` 已有独立二态、常失效率/修复率的模块可靠度和稳态可用度计算；这不代表已经支持任意复杂维修系统。
- `packages/solvers/src/ctmc.ts` 接受明确的 Q、p0、times、rewards，依赖本地 Python/SciPy。当前没有从任意架构自动生成状态模型的能力。
- 任务已有隔离的 SQLite、JSON 文档、资产、运行队列、历史快照及任务包。图模型可沿用这些基础，但新增文档仍需领域校验，不能仅依赖 JSON 语法正确。
- 训练专家审核已有独立的参数、机制、输入修订和人工确认契约，应通过显式映射连接，不能由画图功能隐式改写。

## 3. 方案选择

| 方案 | 优点 | 代价及局限 | 判断 |
| --- | --- | --- | --- |
| 统一领域模型＋多视图＋求解编译层 | 同一对象跨图一致，参数与证据可追溯，能做前后端闭环 | 需要建立对象、故障、机制和计算契约 | 推荐 |
| 每一种图分别保存节点和连线 | 独立画图较快 | 同一部件参数重复，部署与 RBD 容易脱节，难保证计算一致性 | 不满足核心目标 |
| 集成完整外部 MBSE/通用绘图平台 | 图形种类和格式较多 | 内网分发、二次开发、语义映射及运行依赖扩大 | 后续作为导入适配器方向 |

推荐采用 React Flow 承载交互画布，ReMAP 自己持有领域 JSON、命令历史、校验及求解语义。画布库不承担可靠性推导。依赖打入本地构建和离线包，不依赖 CDN 或在线服务。具体兼容版本在实施时通过现有 React 19、TypeScript、Vite 构建验证后锁定。

## 4. 用户操作与四类图

在任务内增加“系统建模”入口。现有独立 RBD 工具可以导入到建模区，历史 JSON 求解方式保留。

界面由左侧对象树/图纸列表、中间画布、右侧属性面板、底部问题与结果区域组成。原生 Agent 使用已有折叠/独立打开能力，避免同屏挤压属性面板。小屏使用全屏画布与抽屉式属性编辑，并提供对象/关系表格替代拖拽。

共同能力：新增对象、引用已有对象、拖动、连线、分组/子图、缩放、搜索定位、撤销/重做、保存状态、自动排版、JSON 导入导出及 SVG/PNG 导出。自动排版须显式触发；刷新恢复已保存位置。提供按钮或表格方式完成新增、关联、编辑、删除，关键操作不能只依赖鼠标拖拽。

| 图类型 | 表达内容 | 特有行为 |
| --- | --- | --- |
| 架构图 | 系统/子系统、部件、服务、接口及依赖 | 支持层级折叠和接口关系；允许真实架构中的反馈环 |
| 部署图 | 站点、机柜、主机、进程、实例、网络/供电故障域 | 以容器和部署关系显示归属；能定位共享故障域 |
| 功能流 | 功能、输入输出、执行顺序、分支、并行及功能承载者 | 流程节点与组件用“由谁实现”关联；分支条件单独记录 |
| RBD | 给定目标、场景和指标下的成功条件 | 以横向串联、并联分支、k/n 组和子框图显示；参数和结果可叠加 |

单击对象，在侧栏显示“基本信息、故障模式、可靠性机制、证据、关联图、关联运行”。跨图选择通过对象 ID 联动；同一对象在同一图多次出现也不复制参数。

总览支持按需叠加故障影响和机制关系；全量信息仍保存在模型中。筛选隐藏的内容必须有计数和范围说明。图例同时使用线型、图标及文字，不能只靠颜色表达含义。

## 5. 统一 JSON 模型

每个任务可有多份系统模型；每份模型包含多个视图和多个分析案例。存储和导出都是有版本的领域 JSON，前端节点对象由它派生。

| 顶层字段 | 内容与约束 |
| --- | --- |
| `schemaVersion` | 语义版本；显式迁移，未知主版本拒绝覆盖导入 |
| `id`, `name`, `revision` | 模型身份、名称及乐观锁版本，服务端生成版本 |
| `entities` | 系统、部件、软件服务、部署实例、功能、接口、位置/故障域等；稳定 ID 与类型 |
| `relations` | contains、deployedOn、connectsTo、dependsOn、implements、flow 等有类型关系；端点必须存在 |
| `failureModes` | 对象归属、故障来源分类、影响、数据参数、来源及适用条件 |
| `mechanisms` | 检测、隔离、重试、恢复、冗余、切换等机制与参数 |
| `mechanismBindings` | 机制作用对象/故障/关系/分析案例、作用类型、顺序、启用条件 |
| `analysisCases` | 目标功能、成功逻辑、故障范围、指标、任务窗口、假设及机制配置 |
| `views` | 图类型、对象引用、显示实例、坐标、尺寸、分组及布局修订 |
| `evidence` | 来源引用、版本/摘要、说明及任务内验证记录 |
| `extensions` | 命名空间化的场景扩展数据；保留未知数据，不执行其中内容 |

稳定 ID 规则：entityId 表示同一个建模对象，occurrenceId 表示一次画面出现，eventId 表示同一个随机事件。不能混用。例如两台相同型号服务器是两个实例，分别失效时用不同事件；它们共用的电源失效引用一个公共事件。

实例可引用类型模板，但数量聚合不代表概率独立，也不自动展开成大量事件。相同型号、重复画面和共享事件三者必须在属性面板区别显示。

参数统一为带单位与来源的量，例如 `{"value":1000,"unit":"FIT","evidenceRefs":["e1"]}`。示例值仅用于合成测试，不能当作真实设备数据。时间支持秒、分钟、小时，后端规范到小时；FIT 规范到每小时失效率并保留原单位和原值。

缺失值用 null/未配置状态表示；0 是有效数值，不能用 0 或默认 1 冒充未知参数。额定失效率、条件失效率、区间、样本量、环境、负载及来源分别存储。手工假设可计算试验结果，但必须标为假设；不能自动产生“证据已验证”。

故障模式支持多种影响及受影响功能。同一次故障造成中断和数据错误时仍是一条事件；影响标签不能把失效率重复相加。部件总失效率与故障模式分解只能选择一个数值来源；输入比例需校验分解规则，禁止与总率叠加。

实体、关系及参数的 JSON 路径均可被校验问题和分析映射引用。图形库专用状态不作为领域 schema 的必需部分，便于内网适配及未来更换画布。

## 6. 多故障维度与 RBD 语义

两种操作分开：

1. **显示筛选**：按硬件/软件/网络/供电等来源、或中断/降级/静默错误等影响过滤和高亮。只改视图，不改变计算。
2. **建立分析案例**：把选定范围明确保存为一个计算场景，记录参与事件、排除事件和排除规则，产生独立案例与结果。不会因为临时隐藏节点就重算。

按来源计算的维度案例默认表示“其它来源事件不发生”的条件分析，必须在图和报告标识；它不是全系统综合可靠度。不同维度结果不能直接相加。综合案例使用联合事件集、稳定 eventId 和明确成功条件。

按功能影响分析时，成功条件必须指定受保护功能和阈值。例如：允许单机退出但吞吐不低于目标、不中断服务、或输出无静默污染；这些目标不一定对应同一张 RBD。

仅有失效率和恢复时间时，系统只能生成待连接的组件/故障框及参数；无法由这些数值唯一推断串并联关系。用户需定义功能依赖或使用经确认的场景模板。由架构生成候选 RBD 时显示映射预览和未决关系，确认后才写入案例。

首轮可计算 RBD 使用显式串联、并联、k/n、事件及子图逻辑；画布中的插入串联块、添加并联支路、建立 k/n 组和重新归组命令直接修改同一份成功逻辑。视觉连线由逻辑生成，不另存一套可与逻辑冲突的可执行连线。

支持一般架构自由连线，但任意桥接、动态切换、环路不能被偷偷转成串联树。首轮超出结构化 RBD 的拓扑允许保存在架构图并显示未支持诊断，定量编译拒绝执行该范围。旧 `tree/events` 导入按旧概率语义保存：仅有概率时不反推 FIT 或恢复时间；RBD/FTA 的成功与失效概率不能相互误用。

## 7. 机制如何入图、如何入计算

机制作为有稳定 ID 的领域对象，可显示为组件徽标、虚线作用边和独立机制子图。属性包括实施状态（候选/已部署/禁用）、前置条件、覆盖故障、依赖资源、检测/隔离/切换/恢复阶段、参数证据和计算支持状态。

| 机制 | 图形表达 | 首轮数值处理 |
| --- | --- | --- |
| 主动冗余、独立多通道、k/n | 独立实例及并联/k/n 成功组 | 按明确拓扑参与静态求解；不能同时再乘“冗余增益” |
| 已确认的故障率改善 | 机制作用边及原始/条件 FIT | 明确适用故障、条件与替代值后重算，保留原值和证据 |
| 已确认的恢复时间改善 | 故障节点恢复参数及机制链 | 修改适用可修复模型的恢复参数；不中断任务可靠度不因此提高 |
| 检测、故障切换、重试、检查点 | 检测→隔离→恢复流程、覆盖率、延迟、依赖 | 保存和定性展示；仅通过已实现且校验通过的模型适配器参与计算 |
| 共享电源、网络域等共同原因 | 故障域容器、同 ID 事件、影响连线 | 可显式建模的公共原因只计算一次；任意相关性不能假设独立 |

多个机制作用于同一参数时必须指定明确优先/组合规则；未指定则报冲突，不相加、不相乘、不使用任意最后一个值。已部署机制作为基线固定；对候选机制做比较必须产生独立场景及新运行。

动态机制缺少状态模型时，可以做明确命名的静态基线分析，但不能把结果显示成“包含全部机制的可靠度”。候选方案比较展示的是同口径重新求解的差值；贡献分摊继续遵守已有 Shapley 约束。

训练场景：图内机制可关联现有专家事件、机制和冻结运行。应用参数变更先产生字段级映射预览，确认后走现有设计修订与签认失效流程。映射适用性和训练场景损失逻辑由现有求解器决定；不能把 RBD 成功概率标成正确有效产出。

## 8. 定量编译与结果追溯

新增纯领域编译层，输入为系统模型不可变快照和 analysisCaseId，输出为规范化求解输入、诊断、假设、参数转换清单和对象→事件→求解输入路径映射。前后端共用 schema，服务端重新校验并编译，不信任客户端提交的计算概率。

首轮实现：

- 直接成功概率模式：兼容旧 RBD；概率必须在 [0,1]，重复事件值冲突时报错。
- 常失效率任务可靠度：明确非修复、不中断任务口径，`R(t)=exp(-lambda*t)`。恢复时间可以展示，但不代入该指标。
- 独立二态稳态可用度：`A=1/(1+lambda*MTTR)`，适用条件明确后把组件可用概率编译到同一成功结构。该值不是任务期间无故障概率。
- 同一部件互斥失效状态、不同修复过程或共享维修资源，不把各模式当作独立二态部件直接相乘。首轮要求明确、已校准的组件聚合参数，或使用已有 CTMC 显式状态输入；不自动伪造等效 MTTR。
- 检测、切换延迟、维修竞争、负载转移等一般动态机制可保存和定性分析，但本轮不承诺通用自动 CTMC/仿真编译器。已存在的训练模型仍按其原契约求解。

所有量的原始值、单位、转换值及转换规则进入快照。统计区间只有在输入模型与相应算法实际支持时才显示，不能为确定性计算虚构 95% 区间。

运行继续进入现有队列，支持取消、失败诊断和历史重放。运行保存模型快照、案例、semanticHash、编译器/求解器版本、编译产物、诊断和追溯映射。图中只能回填该快照的结果；当前模型已变化时标记旧结果，提供“打开运行时模型”。

为新编译产物建立专用运行包装层，将来源元数据与求解器输入分开传递。例如现有 CTMC 拒绝未知字段，不能把 modelSnapshot 直接混进其 Q 输入。

结果覆盖首轮真实支持的系统和部件指标、故障/参数来源、假设及缺口。最小割集、动态重要度、任意相关失效和完整故障注入引擎不属于已有能力，不在图上生成占位数值。

## 9. 后端接口、版本与存储

建议分离 `packages/modeling`（模型、校验、转换、编译）、`apps/api/src/model-routes.ts`（授权、版本、事务）、`apps/web/src/modeling/`（画布与属性）。只在 App 中增加入口和任务上下文，避免继续把编辑器写进单一大组件。

任务级 API 草案：

| 方法与路径（前缀 `/api/tasks/:taskId`） | 行为 |
| --- | --- |
| GET/POST `/system-models` | 列表、新建空模型或复制模板 |
| GET `/system-models/:modelId` | 获取最新保存模型及版本 |
| PUT `/system-models/:modelId` | 全文 JSON 保存，必须附 expectedRevision |
| POST `/system-models/:modelId/validate` | 结构、引用、单位、计算准备度校验，不执行计算 |
| POST `/system-models/:modelId/compile` | 编译已保存版本的指定案例，返回映射及诊断 |
| POST `/system-models/:modelId/runs` | 以 expectedRevision 和案例创建冻结运行；保留幂等键 |
| GET `/system-models/:modelId/export` | 导出领域 JSON，包含内容摘要和版本 |
| POST `/system-models/import-preview` | 校验导入、迁移、冲突、缺引用，返回预览 |
| POST `/system-models/import` | 根据预览摘要创建新模型，默认不覆盖 |

模型归属由路由和任务授权决定，不能信任 JSON 内的 taskId。API、MCP 都复用同一领域服务和任务权限；Agent 可读取模型、校验及提出修改，不能通过新接口绕过用户签认或发布审核。首轮不要求自然语言自动生成整套可计算系统模型。

采用现有任务 SQLite，JSON 文档分别记录模型头、不可变版本和运行快照；版本 ID 包含模型身份与修订，存储操作封装为事务，避免 `putDocument` 覆盖历史。所有模型读取核对文档 kind 和任务归属。

- `revision`：每次成功保存递增，冲突返回 409，保留本地未保存稿。
- `semanticHash`：对象、故障、机制、案例及与解释有关的证据；坐标、配色、折叠和缩放不参与。
- `layoutRevision`：视图布局变化单独记录。拖动结束再提交一条命令；不为每个 mousemove 保存版本。
- 现有训练 `inputRevision` 仅在显式应用图到训练的参数映射时变化。

同模型的语义修改会保守标记相关历史覆盖为过期；在未实现精细依赖分析前，不声称能判断任意变更对结果无影响。历史快照本身不可更改。

任务导出、复制、导入必须包含模型及版本；图内引用使用模型内 ID，任务归属由目标任务重新绑定。模型来源指向旧任务的证据保留来源记录，不能绕过目标任务数据授权。现有任务包导入也调用新模型校验，禁止通过任务包绕过单模型导入校验。

## 10. 校验、异常与定性分析

模型允许保存参数未齐的草稿，区分三类状态：结构不合法不能保存；合法但不完整可保存并定位缺口；满足特定分析案例的要求才允许计算。一个案例缺参数不阻止查看其它图。

结构与领域校验包括：重复 ID、悬空引用、非法端点类型、包含关系成环、非法 k/n、概率冲突、未知单位、非有限数、负率/时间、总率与模式率重复计数、共享事件身份冲突和机制作用冲突。

正常架构/功能反馈环允许保存；包含层级和 RBD 可执行逻辑禁止成环。删除“图上出现”只删显示引用；删除领域对象先列出跨图、故障、机制及分析案例引用，要求用户选择处理方式，原子更新并支持撤销。

定性问题面板显示：无承载组件的功能、缺少故障数据的对象、没有机制关联的影响、没有验证证据的机制、共享故障域内的冗余候选等。名称使用“待复核/缺少关联”，不把缺少建模信息直接等同真实系统失效。图上可手动注入“假设该事件失效”的布尔状态，传播到所选静态成功逻辑；这只是模型情景推演，不宣称做过真实故障注入。

已配置但不支持的机制进入所选分析范围时阻止生成误导性全机制结果；允许用户另建明确排除该机制的基线案例，并记录排除项。

导入只接受数据：不执行函数、脚本、HTML、JSON 中的指令或任意文件路径。SVG 导出由受控图元生成，文本转义；外部图片默认不加载。建议初始上限为单模型 5 MiB、2000 个实体、5000 条关系、单视图 500 个显示节点，超过时明确报错并引导拆分子图；具体性能验收见下一节。求解限制单独继承现有编译器/求解器限制，不能用画布容量冒充计算容量。

## 11. 实施拆分与本轮交付

以下为同一需求的分步交付，不是只做第一项后结束：

1. **模型与存储基础**：领域 JSON、schema、任务级接口、修订/快照、两种导入入口校验、合成模板。
2. **四类可编辑视图**：统一对象树和属性面板、架构/部署/功能流/RBD、跨图定位、分组和子图、撤销及本地导出。
3. **故障与机制建模**：两维筛选、故障模式表、机制关系和作用参数、定性诊断、案例范围与成功逻辑。
4. **定量闭环**：概率/常失效率 RBD、受限稳态可用度、编译追溯、运行覆盖、历史快照，以及训练机制/结果的显式关联。
5. **迁移与验收**：旧 RBD 导入、任务包往返、报告图纸与 JSON 附件、内网依赖分发、桌面/小屏和完整相关回归。

本轮必须能画且能保存全部四种图，能在图上展示机制和真实参数，能以明确支持的模型计算并追溯。通用动态系统自动求解、完整 SysML/UML/BPMN 标准工具、实时多人协同、商业绘图格式无损往返及真实故障注入引擎属于后续能力，不能写成已实现。

## 12. 验收案例

主合成案例：双服务实例＋共享网络/供电＋持久化存储＋检查点/恢复机制。建立架构、部署、功能流、RBD 四张图，组件复用同一 ID。

- 修改一个实例的故障率，跨图属性一致；移动节点、改布局或只切换故障筛选不影响数值输入和既有签认。
- 以“硬件×中断”和“软件×静默错误”建立不同案例，导出记录各自事件范围和成功条件；静默错误缺少相应模型时明确显示定性状态。
- 展示共享电源故障能同时影响两台服务器；不能误判为两套独立供电。已部署机制与候选方案分开保存。
- 独立成功概率 0.9 和 0.8：串联 0.72，并联 0.98；独立三个 0.9 的 2/3 组为 0.972；同一事件重复串联仍为该事件概率。
- 失效率 0.001/h、窗口 100h 时任务可靠度为 exp(-0.1)；MTTR=2h 时稳态可用度为 1/1.002；只改善 MTTR 不改变该任务可靠度。
- 同一故障多影响标签不重复计率；同一部件未知依赖的多故障模式不能直接独立相乘；机制重叠无规则时返回具体冲突。
- 失效率未知时可画图和保存，但对应定量案例不可执行；不能显示 100% 或 0% 占位结论。
- 保存、刷新、JSON 导出/导入、任务复制/迁移后对象关联、布局和历史结果完整；跨任务 ID 猜测不能读写其它任务模型。
- 两个浏览器基于同一旧版本保存时第二个得到 409，并保留其本地编辑内容。
- 运行后修改模型，历史结果仍能打开原始图、参数、范围和来源；取消/失败不回填上一轮结果到新案例。
- 桌面验收 100 节点日常编辑和 500 显示节点边界，记录机器与测量结果；超过上限给出可操作诊断。390px 屏幕可查看图、定位对象和编辑属性，页面无整体横向溢出。
- 图纸 SVG/PNG、完整 JSON、运行结果和报告中的 modelId/revision/semanticHash 一致；当前可见筛选不能删减完整附件。

验证层次：领域单元测试、真实 BDD/可修复数值对照、任务 API 集成、Playwright 画布操作与任务包往返、既有专家训练/工作流/报告回归、TypeScript/ESLint/构建及离线包检查。专家大采样长测试仅在触及其数值或明确做复现验收时执行，不误报默认回归覆盖了它。

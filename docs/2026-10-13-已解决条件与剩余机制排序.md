# 已解决条件与剩余机制排序

在可靠性设计工作台的“预算与措施”展开“已解决条件 · 重算剩余机制排序”，自由选择已有条件，再运行评估或通过Agent选择全自动流水线。

- **已部署机制**：例如静默即时检测已经部署。它在每个候选、每个剩余子集和独立复核中保持启用，故障仍可能发生，按实际覆盖率、成功率和恢复开销计算。已部署措施不再参与新增收益排名或新增成本。
- **假设已完全消除的故障**：按中断、亚健康、静默分组，可全选某类或单选任意事件。仅在本次条件情景中将选定事件的FIT置零，不改写故障库。这是情景假设，不能直接证明工程上零风险。部分降低FIT请在“故障与证据”填写实际剩余发生率。

可同时选择多种故障和已部署机制，也可填写说明。例如静默事件全部消除后，重新查看弹性恢复、进程调度、检查点等其余候选的价值。没有选条件时保持原始基线。清除选择后须重新评估。

结果顶部的“剩余机制排序”支持切换两种依据：

1. 单项增量：在固定基线B上只增加机制i，计算A(B+i)−A(B)。适合比较下一项单独部署的价值。
2. 条件Shapley：在固定B上枚举剩余候选子集，分摊A(B+S+i)−A(B+S)。适合解释组合中各项的贡献，不能当作固定实施顺序。

排序按收益均值，报告保留95%采样区间、负收益和新增正确小时。区间重叠时不能据此证明名次显著。Shapley仅计所选剩余候选，不代表全局最优；未启用或参考规模不计算时只提供单项排名。所有候选都已部署时显示没有剩余候选。

本次的目标分配、建议组合、敏感性和独立复核也使用同一基线，避免按新条件排序却沿用旧方案收益。建议组合载入时保留已解决条件；评估输入、过程快照、HTML/Markdown/JSON报告中保留条件及原始FIT。编辑条件会使原流程过期，需用新版本重新评估。

Agent调用仍使用标准MCP：在audit输入增加 `baseline: { mechanisms: ["sdcDetect"], resolvedEventIds: [], note: "检测已部署，覆盖率按当前参数" }`，通过现有设计保存及求解接口传递。选择已消除事件时使用故障库事件ID，不能用机制ID代替。协议与通用固定基线/边际排序模块独立于OpenCode；当前前向实现覆盖专家训练审核，其他产品需要相应求解器的条件映射。

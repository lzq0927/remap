# 四步工作台重构

2026-11-17。本次把默认界面重构为一个四步工作台：**目标分配 → 可用度评估 → 机制设计 → 机制验证**。四步共用一份模型和一套公式，每一步只有一页。原有界面完整保留为“专家模式”。

## 为什么重构

原任务页把周度场景、四部分流程、架构图谱、事件库、分配编辑、分析工作台等内容叠在同一页，一屏约 6600 像素，重点不清。更根本的问题是数据分散：周度模型、审核事件库和 AGREE 分配各有一套输入，改一处参数不能直接看到对目标差距的影响。

重构后的原则：

1. **一份模型。** 架构模块 → 故障模式 → 可靠性措施。四步都只读写它。
2. **一套口径。** 分配、评估、设计都在“损失负荷 ρ”上进行，结果可以直接比较、相加和闭合。
3. **一步一页。** 每页先给结论，再给明细；方法说明默认收起。
4. **参数都可调。** 规模、窗口、目标、每个模块的故障率与恢复参数、每项措施的取值都能改，改后即时重算并自动保存。

### 架构图

架构图按“分组 → 上级部件 → 模块”画成嵌套的框，网络这类路径型分组按顺序串联并画箭头。每个模块框上标出可用度与目标、每卡 FIT、MTBF、损失时间与预算，以及是否超预算；分组和上级部件的数值由内部模块合成（损失负荷相加）。

- 第 1 步显示目标：各模块的目标可用度和损失预算。
- 第 2 步显示现状，可切换到设计后；点击模块可修改它的故障模式。
- 第 3 步显示设计后，可切换回现状。

画法由两个字段决定，都在“基础库配置 → 架构模块”里修改：分组的画法（并列摆放或串成路径）和模块的上级部件（相同名称的模块被框在一起）。

### 基础库配置

顶栏的“基础库配置”打开三张表，四个步骤共用，修改立即生效：

- **故障模式库**：每种故障模式的所属模块、类型、单件故障率、检出率、检测 / 恢复 / 回滚重算时间、漏检单次损失、影响系数和数据来源。
- **可靠性措施库**：每项措施的方向、作用范围、参数变化、适用比例、证据状态和出处；可新增、编辑、删除，也可把默认库里缺少的条目补回来。
- **架构模块**：分组、模块、上级部件、每卡数量和重要度。

三张表可以整体导出为一个 JSON 文件，再导入到别的任务。基础库目前按任务保存，没有跨任务共享的公共库。

## 方法

### 评估：串联可修系统的更新报酬模型

训练任务是串联系统，任何模块故障都会打断任务；任务停机时不产生新故障。

- 事件率：λᵢ = FITᵢ × 每卡数量 × 卡数 / 10⁹（次 / 运行小时）。
- 单次等效损失：MTTRᵢ = κ · [ c · (检测 + 恢复 + 回滚重算) + (1 − c) · 漏检损失 ]。c 为检出率，κ 为影响系数（事件期间损失的产能比例）。
- 损失负荷：ρ = Σ λᵢ·MTTRᵢ，含义是每运行 1 小时平均损失多少小时。ρ 对故障模式和模块可加。
- 系统可用度：**A = (1 − 公共开销) / (1 + ρ)**。公共开销是与故障无关的固定损耗，例如保存检查点。
- 模块可用度 Aᵢ = 1 / (1 + ρᵢ)，是只有该模块出故障时的系统可用度。
- 模块损失时间 = 窗口 × ρᵢ / (1 + ρ)。各模块之和加公共开销损失等于窗口 × (1 − A)。

这个式子在任何损失水平下都成立。原周度模型用“1 − 损失 / 窗口”，损失大时会算出负数。

### 分配：把允许的损失负荷分给模块

由目标 A* 得到系统允许的损失负荷 ρ* = (1 − 公共开销) / A* − 1，再按权重分给模块：ρᵢ* = wᵢ·ρ\*，Σwᵢ = 1。权重合计为 1，所以模块目标合成后恰好回到系统目标。

| 方法       | 权重               | 适用                                                                                           |
| ---------- | ------------------ | ---------------------------------------------------------------------------------------------- |
| AGREE      | wᵢ ∝ nᵢ / ωᵢ       | 有架构和器件清单的设计阶段。nᵢ 为复杂度（默认取固有失效率，也可取部件数量或手填），ωᵢ 为重要度 |
| ARINC 比例 | wᵢ ∝ 现状 ρᵢ       | 各模块改进难度相近，沿用现状结构                                                               |
| 等分配     | wᵢ = 1 / k         | 早期缺数据时的粗略起点                                                                         |
| 最小改进量 | ρᵢ\* = min(ρᵢ, ρ₀) | 把改进集中在损失最大的几个模块                                                                 |
| 自定义     | 手填               | 已有合同指标或上级分配                                                                         |

每个模块的预算给出两种等价的兑现方式，对应两个改进方向：保持现状恢复能力时要求每卡 FIT ≤ 某值（提升 MTBF），或保持现状故障率时要求单次等效损失 ≤ 某值（降低 MTTR）。

AGREE 不使用现状的恢复能力，所以它会把“故障不多但单次损失很大”的模块暴露出来。默认场景里 AICore 静默故障只有 67 FIT，却占了最大的一块损失，AGREE 下它超预算数百倍；ARINC 则会给它最大的预算。两种视角都有用，界面提供四种方法的并排对比。

### 设计：措施、贡献与推荐

措施分两个方向。提升 MTBF 的措施改故障率 FIT；降低 MTTR 的措施改检出率、检测时间、恢复时间、回滚重算、漏检损失或影响系数。一项措施可以同时改几个参数，取值方式有三种：在现值上按比例降低、直接设为新值、在现值上增加（用于表达代价，例如校验带来的吞吐损失）。

措施不一定对所有故障都有效，所以每项措施有一个**适用比例**：所作用的故障中，措施实际适用并成功的比例。参数按它在现值与目标值之间折算，例如“重执行成功时 5 秒恢复，适用 80%”等于恢复时间取 0.8 × 5 秒 + 0.2 × 现值。

多项措施作用于同一参数时结果与顺序无关：多项“设为”只取改善最大的一项，不叠加；多项“降低”连乘（检出率的“降低”作用在漏检率上）；“增加”逐项累加。几项缩短恢复时间的措施同时启用时因此不会重复计收益，这是偏保守的处理。

- **贡献**按 Shapley 值分摊：对所有启用顺序求平均边际收益。各项之和恰好等于设计后相对现状的提升。启用的措施不超过 14 项时精确枚举，更多时用固定种子的排列抽样。
- **推荐方案**：在已启用措施的基础上，按数量从少到多穷举其余措施的组合，找到的第一组即数量最少；数量相同时优先证据更充分的，其次选可用度更高的。候选很多、穷举不完时，改为逐步加入提升最大的措施，达标后再剔除可以去掉的项：这时每一项都不可少，但不保证数量最少，界面会注明。措施库用尽仍不够时，按 ρ 与 ρ\* 的比值给出还需整体降低的比例。
- **参数反推**：其余措施不变，用二分法求某个参数取多少刚好达标；做到极限也不够时如实说明。

### 验证：独立仿真

仿真不使用解析公式。故障按事件率随机到达，按检出率随机决定是否检出；恢复时间取指数分布，回滚重算取均匀分布，漏检损失取指数分布；窗口结束时截断未完成的恢复。现状和设计后使用不同的随机数流，默认每次更换种子。

五项判定：

1. 仿真均值的 95% 置信区间下限不低于目标。
2. 达到目标的窗口比例不低于要求（默认 90%，可调）。
3. 仿真与解析结果的偏差在容差内（3 倍标准误与 0.5 个百分点中较大者）。
4. 各模块的仿真损失不超过第 1 步的分配预算。
5. 所选措施都标记为有实测证据。

前四项是数值判定。第五项不影响数值，但未满足时结论为“数值达标，仍有待确认项”：仿真只能证明参数成立时可以达标。

## 默认场景

50 万卡、168 小时窗口、目标 95%。数值都是可编辑的场景输入，不代表厂商实测失效率。

- **架构**：5 个分组、11 个模块。计算（NPU 模组内的 AICore、NPU 其余部分、HBM，以及节点与板级）；网络（IO Die 与 L1 互联 → 光模块 → L2 / Leaf / Spine 与网卡）；存储；供电与冷却、管理面；软件与未归因。
- **故障模式**共 14 种：10 种中断、2 种静默、2 种亚健康。
  - 故障率取自 2026-11-12 周度用户场景：每卡 HBM＋NPU 合计 1700 FIT，各占全部故障 15%；光模块占 35%（单只 500 FIT，按每卡约 4 只折算）；静默故障占 1.4%，其中 AICore 占 85%，检出率 90%，漏检恢复 48 小时。
  - 其余 35% 的模块拆分，以及其中亚健康的份额，按 2026-10-14 基线故障库各对象的相对构成折算，属先验。
  - 亚健康不中断任务，只降速 5%；检测等待和漏检损失已按降速比例折算成等效停机时间。
- **恢复链**取自现有评估模型的基线参数：95% 在 10 秒检出、其余 60 秒超时；恢复 180 秒、成功率 99%、失败后人工追加 2 小时；检查点周期 300 秒、保存 4 秒（公共开销 1.32%）。
- **措施库**共 29 项，提升 MTBF 6 项、降低 MTTR 23 项：
  - 用户给出的 4 项，默认启用：HBM 纠错降 60%、AICore 静默压测筛查降 60%、光模块 500 → 50 FIT、静默检出率 90% → 95%。
  - 现有基础机制的其余 7 项：中断快速检测、亚健康快速检测、静默故障干净 step 恢复、通信与算子重执行、进程级快速恢复、域级弹性恢复、更频繁的检查点。作用范围按基线故障库中各机制适用的故障对象映射。
  - 现有扩展机制库的 16 项（FP8 与 FP4 两条路径的静默检测合为一项，共 15 项）：链路透明恢复、网络绕行与降级运行、故障隔离与传播抑制、控制面异常下业务连续运行、预热进程、运行时初始化快照、异步检查点保存、无损检查点压缩、故障分类与恢复动作匹配、算子 ABFT 校验、网络端到端静默检测、在线压测与异常资源筛除、HCCL 通信域弹性重建、CANN 图准备与启动缓存等。
  - 本工作台补充的 3 项：漏检静默故障定期校验（设计假设）、内存故障预测与主动隔离、供电冗余与器件降额（后两项是示例，取值没有现成来源）。

扩展机制库中有几项没有给出适用比例或成功率（原库标注为待测）。这些措施的适用比例暂取 50%，FP8 / FP4 路径的份额未知、暂取 0，均在措施的依据里写明，需要按故障注入结果修改。

默认场景的解析结果：

| 状态                    | 可用度 |
| ----------------------- | ------ |
| 现状                    | 65.05% |
| 启用用户给出的 4 项措施 | 79.69% |
| 再启用推荐的 8 项       | 95.24% |
| 29 项全部启用           | 96.24% |

现状 65.05% 与周度场景给出的参考值 60% 接近但不相同；差异来自其余 35% 故障的拆分和恢复链参数都是先验。用户给出的 4 项措施不足以达到 95%，主要差距在中断类故障的单次损失和静默故障的漏检分支。

推荐的 8 项是：域级弹性恢复、漏检静默故障定期校验、更频繁的检查点、异步检查点保存、故障分类与恢复动作匹配、算子 ABFT 实时矩阵校验、通信与算子重执行、供电冗余与器件降额。候选有 25 项，这一组是逐步选取的结果，不保证数量最少。达标余量只有 0.24 个百分点，独立仿真中达到目标的窗口约占 85%，低于默认 90% 的要求，需要再加措施留出余量。

## 已知边界

- 故障按恒定失效率到达，不含早期失效和耗损期。
- 静默故障的漏检损失按等效停机时间计入。实际是已完成的训练被作废，期间系统仍在运行并可能再出故障。
- 不考虑多个故障同时发生时共享一次恢复，也不区分瞬态与永久故障的备件等待。
- 影响系数小于 1 的事件按等效停机时间计入。
- 置信区间只反映随机抽样误差，不含故障率与恢复参数本身的不确定性。
- 新模型与专家模式的事件库、六阶段记录相互独立，不自动同步。需要 54 类事件、检查点逐事件账本或专家引擎复现时，使用专家模式。

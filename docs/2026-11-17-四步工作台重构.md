# 四步工作台重构

2026-11-17。本次把默认界面重构为一个四步工作台：**目标分配 → 可用度评估 → 机制设计 → 机制验证**。四步共用一份模型和一套公式，每一步只有一页。原有界面完整保留为“专家模式”。

## 为什么重构

原任务页把周度场景、四部分流程、架构图谱、事件库、分配编辑、分析工作台等内容叠在同一页，一屏约 6600 像素，重点不清。更根本的问题是数据分散：周度模型、审核事件库和 AGREE 分配各有一套输入，改一处参数不能直接看到对目标差距的影响。

重构后的原则：

1. **一份模型。** 架构模块 → 故障模式 → 可靠性措施。四步都只读写它。
2. **一套口径。** 分配、评估、设计都在“损失负荷 ρ”上进行，结果可以直接比较、相加和闭合。
3. **一步一页。** 每页先给结论，再给明细；方法说明默认收起。
4. **参数都可调。** 规模、窗口、目标、每个模块的故障率与恢复参数、每项措施的取值都能改，改后即时重算并自动保存。

## 方法

### 评估：串联可修系统的更新报酬模型

训练任务是串联系统，任何模块故障都会打断任务；任务停机时不产生新故障。

- 事件率：λᵢ = FITᵢ × 每卡数量 × 卡数 / 10⁹（次 / 运行小时）。
- 单次等效损失：MTTRᵢ = κ · [ c · (检测 + 恢复 + 回滚重算) + (1 − c) · 漏检损失 ]。c 为检出率，κ 为影响系数（事件期间损失的产能比例）。
- 损失负荷：ρ = Σ λᵢ·MTTRᵢ，含义是每运行 1 小时平均损失多少小时。ρ 对故障模式和模块可加。
- 系统可用度：**A = (1 − 公共开销) / (1 + ρ)**。公共开销是与故障无关的固定损耗，例如保存检查点。
- 模块可用度 Aᵢ = 1 / (1 + ρᵢ)，是只有该模块出故障时的系统可用度。
- 模块损失时间 = 窗口 × ρᵢ / (1 + ρ)。各模块之和加公共开销损失等于窗口 × (1 − A)。

这个式子在任何损失水平下都成立。原周度模型用“1 − 损失 / 窗口”，损失大时会算出负数。

### 分配：把允许的损失负荷分给模块

由目标 A* 得到系统允许的损失负荷 ρ* = (1 − 公共开销) / A* − 1，再按权重分给模块：ρᵢ* = wᵢ·ρ\*，Σwᵢ = 1。权重合计为 1，所以模块目标合成后恰好回到系统目标。

| 方法       | 权重               | 适用                                                                                           |
| ---------- | ------------------ | ---------------------------------------------------------------------------------------------- |
| AGREE      | wᵢ ∝ nᵢ / ωᵢ       | 有架构和器件清单的设计阶段。nᵢ 为复杂度（默认取固有失效率，也可取部件数量或手填），ωᵢ 为重要度 |
| ARINC 比例 | wᵢ ∝ 现状 ρᵢ       | 各模块改进难度相近，沿用现状结构                                                               |
| 等分配     | wᵢ = 1 / k         | 早期缺数据时的粗略起点                                                                         |
| 最小改进量 | ρᵢ\* = min(ρᵢ, ρ₀) | 把改进集中在损失最大的几个模块                                                                 |
| 自定义     | 手填               | 已有合同指标或上级分配                                                                         |

每个模块的预算给出两种等价的兑现方式，对应两个改进方向：保持现状恢复能力时要求每卡 FIT ≤ 某值（提升 MTBF），或保持现状故障率时要求单次等效损失 ≤ 某值（降低 MTTR）。

AGREE 不使用现状的恢复能力，所以它会把“故障不多但单次损失很大”的模块暴露出来。默认场景里 AICore 静默故障只有 67 FIT，却占了最大的一块损失，AGREE 下它超预算数百倍；ARINC 则会给它最大的预算。两种视角都有用，界面提供四种方法的并排对比。

### 设计：措施、贡献与推荐

措施分两个方向。提升 MTBF 的措施改故障率 FIT；降低 MTTR 的措施改检出率、检测时间、恢复时间、回滚重算、漏检损失或影响系数。取值方式有两种：在现值上按比例降低，或直接设为新值。多项措施作用于同一参数时结果与顺序无关（“设为”取更优值，“降低”连乘，检出率的“降低”作用在漏检率上）。

- **贡献**按 Shapley 值分摊：对所有启用顺序求平均边际收益。各项之和恰好等于设计后相对现状的提升。措施不超过 14 项时精确枚举，更多时用固定种子的排列抽样。
- **推荐方案**：在已启用措施的基础上枚举其余措施的组合，取能达标的最少一组；数量相同时优先证据更充分的，其次选可用度更高的。措施库全部启用仍不够时，按 ρ 与 ρ\* 的比值给出还需整体降低的比例。
- **参数反推**：其余措施不变，用二分法求某个参数取多少刚好达标；做到极限也不够时如实说明。

### 验证：独立仿真

仿真不使用解析公式。故障按事件率随机到达，按检出率随机决定是否检出；恢复时间取指数分布，回滚重算取均匀分布，漏检损失取指数分布；窗口结束时截断未完成的恢复。现状和设计后使用不同的随机数流，默认每次更换种子。

五项判定：

1. 仿真均值的 95% 置信区间下限不低于目标。
2. 达到目标的窗口比例不低于要求（默认 90%，可调）。
3. 仿真与解析结果的偏差在容差内（3 倍标准误与 0.5 个百分点中较大者）。
4. 各模块的仿真损失不超过第 1 步的分配预算。
5. 所选措施都标记为有实测证据。

前四项是数值判定。第五项不影响数值，但未满足时结论为“数值达标，仍有待确认项”：仿真只能证明参数成立时可以达标。

## 默认场景

50 万卡、168 小时窗口、目标 95%。数值都是可编辑的场景输入，不代表厂商实测失效率。

- **故障率**取自 2026-11-12 周度用户场景：每卡 HBM＋NPU 合计 1700 FIT，各占全部故障 15%；光模块占 35%（单只 500 FIT，按每卡约 4 只折算）；静默故障占 1.4%，其中 AICore 占 85%，检出率 90%，漏检恢复 48 小时。
- **其余 35%** 的模块拆分按 2026-10-14 基线故障库各对象的相对构成折算，属先验。
- **恢复链**取自现有评估模型的基线参数：95% 在 10 秒检出、其余 60 秒超时；恢复 180 秒、成功率 99%、失败后人工追加 2 小时；检查点周期 300 秒、保存 4 秒（公共开销 1.32%）。
- **措施库**共 9 项。默认启用用户给出的 4 项：HBM 纠错降 60%、AICore 静默压测筛查降 60%、光模块 500 → 50 FIT、静默检出率 90% → 95%。另 5 项候选取自现有机制库的参数：漏检定期校验、中断快速检测、进程级快速恢复、快速检查点、域级弹性恢复。

默认场景的解析结果：

| 状态                                            | 可用度 |
| ----------------------------------------------- | ------ |
| 现状                                            | 65.05% |
| 启用用户给出的 4 项措施                         | 79.69% |
| 再启用推荐的 2 项（漏检定期校验、域级弹性恢复） | 96.63% |
| 9 项全部启用                                    | 96.99% |

现状 65.05% 与周度场景给出的参考值 60% 接近但不相同；差异来自其余 35% 故障的拆分和恢复链参数都是先验。用户给出的 4 项措施不足以达到 95%，主要差距在中断类故障的单次损失和静默故障的漏检分支。

## 已知边界

- 故障按恒定失效率到达，不含早期失效和耗损期。
- 静默故障的漏检损失按等效停机时间计入。实际是已完成的训练被作废，期间系统仍在运行并可能再出故障。
- 不考虑多个故障同时发生时共享一次恢复，也不区分瞬态与永久故障的备件等待。
- 影响系数小于 1 的事件按等效停机时间计入。
- 置信区间只反映随机抽样误差，不含故障率与恢复参数本身的不确定性。
- 新模型与专家模式的事件库、六阶段记录相互独立，不自动同步。需要 54 类事件、检查点逐事件账本或专家引擎复现时，使用专家模式。

# 内网部署、开发与单向迭代指南

本指南适用于公司不允许代码和数据外传、内网模型能力有限的场景。推荐结构是：外网强模型开发通用核心，软件版本经审核单向进入内网；内网模型在固定接口和测试约束下完成企业适配。内网代码、真实数据、提示词、运行轨迹、故障日志与报告全部留在内网。

## 1. 仓库与资产布局

建议由公司建立三个独立位置，而不是在一个外网 Git 仓库中放所有内容：

```text
D:/reliability/
  core/                # 内网 Git：导入的通用核心 + 必要的内网补丁
  adapters/            # 内网 Git：企业解析/映射规则与本地测试
  local/               # 不进 Git：internal.json、运行 .env、模型密钥
  data/                # 内网数据：任务、故障库、机制库、结果与历史
  delivery/            # 经批准导入的软件和离线依赖
  runtime/             # 公司批准的 Node、pnpm、OpenCode、Python
```

core 的内网仓库只能配置内网 remote；不配置外网 push remote。adapters 从创建开始就在内网。真实资产通过 DATA_DIR 存储，不进入核心源码库。企业资产库可以有自己的内网版本管理和审核机制。外网私有 Git 也属于外传，不能因“private”就上传。

`.gitignore` 只是防误提交措施；不能证明仓库没有企业内容。每次导出和提交仍需检查实际文件清单。内网 `export:release` 会拒绝生成通用外网发布包，任务导出功能仍可用于内网迁移，使用它不代表允许外传。

## 2. 外网准备交付

只在通用核心、公开参考和独立合成输入上操作。先完成回归，再导出软件包：

```powershell
pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm export:release
pnpm offline:prepare --output artifacts/offline-deps-win32-x64
pnpm offline:verify --bundle artifacts/offline-deps-win32-x64
pnpm offline:verify --bundle artifacts/offline-deps-win32-x64 --install --destination artifacts/offline-install-check
```

目录已存在会报错，请使用新的目录；工具不会自动删除或覆盖。`offline:prepare` 用独立 pnpm store 按锁文件下载依赖，不使用已有 node_modules。旁边的 `.fetch` 目录是准备时的虚拟链接目录，不需要交付。离线包包含 request 描述文件、store 和 manifest，不含任务数据、模型凭据和应用源码。

软件包在 `release/rem-prototype-0.1`；依赖包和软件包分别核验文件摘要。摘要能识别文件变化，不能证明来源可信；公司仍须验证来源、审核依赖和批准导入。

依赖包只覆盖**当前 OS/CPU 架构的 npm 依赖**。须另外供给以下运行时：

| 运行时 | 要求与用途 |
|---|---|
| Node | 24 或更新；本地运行 API 与工具 |
| pnpm | 与 package.json 的 packageManager 完全一致；当前 11.25.0 |
| OpenCode | 本地原生二进制；当前验证基线 1.18.35 |
| Python + NumPy/SciPy | 使用 CTMC 时必需；按目标 Python/平台准备 wheel |
| Playwright 浏览器 | 仅端到端测试必需；按锁文件版本准备浏览器运行时 |
| Agent 模型 SDK/缓存 | 原生 OpenCode 可能使用独立缓存；需在同平台受控环境预置并做断网验收 |

OpenCode 的安装脚本可能在原生包缺失时调用 npm 在线安装。内网安装禁用所有生命周期脚本，使用公司批准的 `OPENCODE_BIN` 指向原生二进制。不要在内网执行在线安装、模型目录更新或浏览器下载来“补齐”。SDK 与原生工具有独立出站行为，npm 离线安装通过不能代替 Agent 断网验收。

Python 可在批准的准备机上根据 `solvers/ctmc/requirements.txt` 下载适配目标环境的 wheel，在内网执行：

```powershell
python -m pip install --no-index --find-links D:/reliability/delivery/python-wheels -r solvers/ctmc/requirements.txt
```

如果准备机和目标机 Python/OS/架构不同，由公司包管理人员选择目标 wheel，不直接复制开发机的 Python site-packages。

## 3. 内网首次部署

将批准的软件与依赖复制到内网。先安装批准的运行时，核验其版本与来源。以下命令在 `D:/reliability/core` 执行，路径可按实际环境调整。

```powershell
node --version
pnpm --version
Copy-Item config/internal.example.json D:/reliability/local/internal.json
Copy-Item config/internal.env.example D:/reliability/local/runtime.env
```

编辑本机 JSON，替换为公司批准的模型 origin、Base URL 和模型 ID。`allowedOrigins` 是精确来源，例如 `https://llm.company.example`，不带 `/v1`、查询、通配符或密钥；`provider.baseURL` 才带 API 路径。它不是自动判定“这个域名属于内网”，白名单内容必须由公司批准。

编辑 runtime.env，指定真实本地目录和本机 OpenCode。密钥仅通过本机环境变量引用；不要把实际密钥写入 JSON、Skill、任务包或核心仓库。若使用独立文件提取模型，必须同时配置 MODEL_BASE_URL、MODEL_ID、MODEL_API_KEY；其来源也必须在批准列表中。结构化 JSON/CSV/XLSX 导入可以完全不用模型。

内网模式要求显式配置绝对 DATA_DIR，且目录位于核心源码之外；缺少该配置、使用源码下的目录或链接指回源码目录会拒绝启动。已有开发任务不会被自动移动或删除，应由内网管理员通过内网任务迁移流程导入。

```powershell
$env:RELIABILITY_ENV_FILE = 'D:/reliability/local/runtime.env'
pnpm offline:verify --bundle D:/reliability/delivery/offline-deps-win32-x64
node scripts/launch.mjs bootstrap --install --store-dir D:/reliability/delivery/offline-deps-win32-x64/store
pnpm run doctor
pnpm build
pnpm agent
```

另开 PowerShell，选择同一个 env 文件，运行 `pnpm start`；打开 `http://127.0.0.1:4178`。开发时用 `pnpm dev` 和 `http://127.0.0.1:5173`。每个终端必须选择同一份内网配置；环境变量已有值优先，不会被 env 文件覆盖。首次部署建议用没有外网模型变量的新终端。

内网 bootstrap 安装强制 `--offline --frozen-lockfile --ignore-scripts`。缺少依赖时会失败，不会回退在线。若忽略安装脚本导致某个本地工具不可用，先由公司批准供给相应二进制，再复验；不直接打开在线脚本。

依赖包应保留批准的原始副本。实际开发可复制 store 到本机工作目录使用，因为 pnpm 会写入本机项目跟踪链接；后续摘要验证应对原始副本执行。`offline:verify --install` 自动复制独立 store，不会修改交付包。

doctor 检查配置与本地求解，不会请求模型。它通过不代表模型能正确工具调用。界面创建一个合成任务后执行：

```powershell
pnpm bootstrap --task <taskId>
pnpm run doctor --task <taskId>
```

在右侧本地 OpenCode 中选择已配置的企业模型，运行 `/sd-dfr-remap`。内网项目配置只启用公司 provider 与当前任务的本地可靠性 MCP，关闭分享和自动更新，拒绝额外项目插件/Agent 配置。若任务目录带有旧的自定义 Agent/插件配置，会提示冲突；管理员检查并处理这些文件，不通过删除检查逻辑规避。

内网仍需使用专用 OS 账号/Agent 配置目录、受控原生 OpenCode 服务和网络出口白名单。若本机已有外网 OpenCode 服务，先在内网停用并启动公司批准的实例；不要把真实任务连接到旧的外网模型配置实例。

内网启动器拒绝静默复用已有 OpenCode 服务。只有管理员核实该服务属于受控内网实例后，才可设置 `RELIABILITY_TRUST_RUNNING_OPENCODE=1`。启动器依据本机 1.18.35 二进制提供的环境开关禁用自动更新、分享、模型目录在线读取、默认插件、外部 Skill 和 Claude 配置导入；原生全局/上级目录配置仍须管理员核查。

## 4. 必须完成的网络与模型验收

应用运行策略对工作台模型请求、API/Agent 地址进行校验，API 与嵌入 OpenCode 要求本机回环；模型只能使用配置批准的来源。它不能约束原生 OpenCode 内部所有请求、全局配置、DNS、重定向以外的网络路径或任意本地程序。**真正的禁止外传由公司网络与执行环境实现。**

内网管理员应只放行批准的公司模型和必要内网服务，阻断外网 HTTPS、DNS 解析外连、隧道与自动更新。然后在阻断条件下逐项确认：启动工作台、启动原生 OpenCode、加载 Skill/MCP、发起模型对话、流式响应、工具调用、保存恢复会话、执行一轮合成评估。检查出口审计，确定模型目录/SDK/插件没有外部访问。工具命令只在该受控环境执行。

本系统仍是本地单用户工作台。多人内网共享需要公司认证、授权、HTTPS 反向代理和审计，不能直接绑定所有网卡就当作企业部署。外网开发期间的临时访问隧道不属于内网交付，也不得在公司内部启动。

## 5. 企业数据适配开发

优先用核心已经支持的 JSON/CSV/XLSX 解析，再由企业映射模块把本地列名、表结构转换成标准输入。适配模块放在独立内网 adapters 仓库，管理员在 internal.json 加入固定 `adapter`（id、version、module 绝对本地路径）。接口说明和合成示例见 `packages/extensions/README.md`、`examples/internal-adapter`。

适配输出只产生映射草稿，仍由核心 mapConfirmedData 校验单位、暴露口径、字段白名单和歧义。输入必须先由用户确认，映射结果不会直接修改训练设计、冻结资产或启动正式交付。预览保留 adapter id/version、输入摘要和来源。管理员安装的模块在服务进程内运行，是可信企业代码，不是可运行任意上传脚本的插件沙箱。

开发一个映射时采用以下顺序：

1. 从合成输入开始定义字段契约；真实格式与真实数据只在内网查看。
2. 明确 FIT=每十亿设备小时、恢复时长单位、影响域、覆盖率/成功率口径；缺失参数写歧义，禁止补零或猜测。
3. 写映射与正向/错误输入测试，确认标准资产预览与来源。
4. 在任务中导入真实文件，人工核对原文、结构化结果与映射预览。
5. 校验并冻结任务私有资产，再用于评估；进入公共资产库另走公司审核。
6. 将适配代码和测试提交**内网 Git**，真实源文件不随核心版本发布。

当前扩展点覆盖结构化映射，不替换 PDF/OCR 引擎、求解器或报告渲染器。复杂企业文件先由独立内网转换工具生成结构化 JSON，保留源文件行/页/单元格与摘要，再调用标准输入接口。后续确需新的解析/求解/报告扩展，先增加契约与金标准测试，再扩展核心接口。

## 6. 内网模型能力有限时怎样开发

降低一次任务的跨度，比让模型“全自动重写系统”更可靠。按 `templates/internal-development-task.md` 给每次开发一个文件或一个接口：允许改动范围、输入输出、错误处理、合成样例、测试命令和通过条件。由开发者审查 diff，运行确定性测试，再进入下一项。

运行时同样采用小步骤：读取任务状态 → 读取相关文件或资产 → 生成结构化草稿 → 校验 → 等待用户确认 → 调用求解 → 检查结果 → 交付。每次只处理当前阶段，阶段版本/输入摘要由 WorkflowService 校验。模型解释不能替代数值结果；Agent 的聊天完成也不能替代工作台阶段确认。

| 任务类型 | 推荐执行者 |
|---|---|
| 通用算法、UI 与接口优化，独立合成回归 | 外网开发通用核心 |
| 企业列映射、接口转换、格式适配 | 内网模型 + 明确契约 + 人工评审 |
| 单位换算、分配、RBD/BDD/FTA/CTMC/仿真 | 本地确定性工具 |
| 参数可信度、拓扑与故障传播假设、设计结论 | 企业专家确认与实测证据 |
| 跨模块架构变更 | 先设计与测试契约；核心通用部分在外网合成验证 |

内网任务失败时，先用测试区分格式/参数错误、适配错误、核心错误、模型编排错误。只让模型修改责任模块，避免每次修改整个核心。记录任务完成率、人工接受率和失败原因到内网运行轨迹，不将该轨迹自动上传。

## 7. 持续导入通用核心版本

首次从外网 Git 导入通用代码须经公司批准。公司机器允许拉取时可使用只读导入；若禁止直连外网，则由批准的介质或单向网闸导入 Git bundle/发布包。导入方式不能包含向外 push 的配置。

推荐 Git bundle：外网仅从审核过且已提交的通用核心版本生成，不使用工作区里未审查的企业文件。示例命令中的分支名用实际版本替换：

```powershell
# 外网核心机：核对提交和文件后生成
git bundle create rem-core.bundle <approved-core-branch>
git bundle verify rem-core.bundle

# 内网已有 core 仓库：从批准介质导入，不设置外网 remote
git bundle verify D:/reliability/delivery/rem-core.bundle
git fetch D:/reliability/delivery/rem-core.bundle <approved-core-branch>:refs/rem-import/core-candidate
git switch -c internal/core-upgrade refs/rem-import/core-candidate
```

内网导入后在升级分支对比上一版，回放现有内网补丁，运行核心回归和企业适配测试，再用真实参数做内网验收。生产工作目录与当前开发分支不要混用。部署前停止服务并备份 DATA_DIR 和本机配置；新版用测试数据目录先验证。应用数据结构迁移应先在备份副本上验收，再处理正式数据。

不要直接覆盖企业 adapters 或 local/data 目录。若升级失败，恢复上一核心版本、上一适配版本和匹配的数据备份；不可只回退源码却继续使用已迁移的数据库。每次交付记录：核心提交/摘要、Skill 版本、MCP 版本、适配 id/version、资产版本/摘要、求解器/依赖版本、模型 ID 及内网部署版本。

## 8. 内网问题怎样推动外网核心改进

公司禁止代码和数据外传时，内网补丁、diff、完整错误日志、截图和模型对话都不能交给外网模型。先判断是否能从公开接口与独立合成数据构造同类问题，按 `templates/approved-synthetic-issue.md` 列清单，经公司审核批准后，才在外网复现和修复通用核心。

“脱敏”不是批准。真实 FIT 的缩放、删除产品名称、替换 IP 等仍可能保留敏感结构。无法构造无关合成复现的问题就在内网修复，补丁留在内网；以后通过已有契约导入新的通用核心时继续回放该补丁。

## 9. 内网验收与日常迭代

通用核心验收使用公开/合成数据；企业验收使用真实数据且记录留在内网。两层缺一不可：

- 首次在未装依赖的目标机器断网安装，核验 npm 包、原生二进制、Python 和 Agent SDK。
- `doctor` 与当前任务 MCP 握手通过；真实企业模型能对话、流式返回并正确使用工具。
- 企业文件映射的字段、单位、源定位和未知值处理全部核对。
- 任务、私有资产与会话隔离；公共资产审核与发布流程单独验收。
- 训练产出指标定义、目标分解假设、共享事件/传播模型和数值金标准通过专家评审。
- 断网出口审计、备份恢复、核心/适配升级和回滚通过。

建议固定节奏：内网收集问题并分类 → 用小任务修复本地适配 → 有条件时申请独立合成问题 → 外网通用修复与回归 → 公司批准导入 → 内网真实数据验收。不要为了等外网版本阻塞已能在内网解决的适配问题。

本轮实现与验证记录见 `docs/内网开发实施与验收.md`。它明确软件已验收范围与必须在公司环境补做的项目。

# 四步工作台重构

2026-11-17。本次把默认界面重构为一个四步工作台：**目标分配 → 可用度评估 → 机制设计 → 机制验证**。四步共用一份模型和一套公式，每一步只有一页。原有界面完整保留为“专家模式”。

2026-11-24 补充了分析逻辑：目标随规模变化、后果大的模块单独指定目标、以周为粒度的频次与单次损失差距、从小到大的恢复阶梯、措施分层，以及改进程度收益、组合收益路径和“重点做哪几项、做到什么程度”的结论。下文按补充后的口径描述。

## 分析主线

整套分析围绕一个恒等式展开：

**每周损失 = 故障频次 × 单次等效损失**

| 步骤       | 回答的问题                 | 方法                                                                                 |
| ---------- | -------------------------- | ------------------------------------------------------------------------------------ |
| 目标分配   | 每个模块允许损失多少       | 系统目标随规模换算；后果大的模块单独指定；其余按 AGREE 等方法分配                    |
| 可用度评估 | 现在损失多少、差在哪       | 频次来自器件失效率，单次损失来自检测与恢复阶梯；差距分别从频次和单次损失两个角度给出 |
| 机制设计   | 做哪几项措施、做到什么程度 | 组件级措施降频次，系统级措施缩短单次损失；看改进程度收益、组合收益路径、Shapley 贡献 |
| 机制验证   | 结论在随机波动下是否成立   | 独立的离散事件仿真，逐级模拟恢复阶梯                                                 |

## 为什么重构

原任务页把周度场景、四部分流程、架构图谱、事件库、分配编辑、分析工作台等内容叠在同一页，一屏约 6600 像素，重点不清。更根本的问题是数据分散：周度模型、审核事件库和 AGREE 分配各有一套输入，改一处参数不能直接看到对目标差距的影响。

重构后的原则：

1. **一份模型。** 架构模块 → 故障模式 → 可靠性措施。四步都只读写它。
2. **一套口径。** 分配、评估、设计都在“损失负荷 ρ”上进行，结果可以直接比较、相加和闭合。
3. **一步一页。** 每页先给结论，再给明细；方法说明默认收起。
4. **参数都可调。** 规模、窗口、目标、每个模块的故障率与恢复参数、每项措施的取值都能改，改后即时重算并自动保存。

## 方法

### 评估：频次、恢复阶梯与系统可用度

训练任务是串联系统，任何模块故障都会打断任务；任务停机时不产生新故障。

**故障频次。** λᵢ = FITᵢ × 部件总数 / 10⁹（次 / 运行小时）。按卡计的模块，部件总数 = 每卡数量 × 卡数；机房供配电这类全系统只有固定几套的设施，部件总数不随规模变化。界面以周为粒度显示频次：每周不到 1 次的写成“每年几次”或“几年 1 次”。

**单次等效损失。** 一次故障的损失由检测和恢复阶梯决定：

1. 检测：以概率 c 被检出，耗时 t检出；否则漏检，过 t发现 之后才被兜底手段发现（静默故障是定期校验或结果异常，中断故障是超时）。
2. 恢复阶梯：从小到大逐级尝试，成功就结束，失败则白费一段时间再升到下一级。

| 级别           | 含义                           | 是否回滚 |
| -------------- | ------------------------------ | -------- |
| 重执行         | 原地重试通信或算子，任务不感知 | 否       |
| 进程重调度     | 只重启并重新调度出错的进程     | 是       |
| 域级弹性恢复   | 只恢复故障域，其余部分继续运行 | 是       |
| 检查点全局恢复 | 全部任务从最近的检查点重启     | 是       |
| 人工恢复       | 自动手段都失败后人工介入       | 是       |

每一级有成功率 pₖ、成功耗时 tₖ、失败白费的时间 fₖ、影响范围 κₖ（这一级期间损失的产能比例，域级恢复远小于 1）。成功率为 0 表示这种故障不走这一级；用到的最后一级视为必然成功。哪些级别可用与故障模式有关：重执行只对瞬时故障有用，亚健康不需要回滚。

MTTRᵢ = κ · [ c·t检出 + (1 − c)·t发现 + Σₖ 到达ₖ·(pₖ·tₖ + (1 − pₖ)·fₖ)·κₖ + Σ需回滚的级别 到达ₖ·pₖ·t回滚 ]

到达ₖ = Π前面各级 (1 − pⱼ)。界面在第 2 步把每个故障模式的恢复链画出来，逐环列出“概率 × 时间”，并与措施生效后的恢复链并排对比。

**系统可用度。**

- 损失负荷：ρ = Σ λᵢ·MTTRᵢ，含义是每运行 1 小时平均损失多少小时。ρ 对故障模式和模块可加。
- 系统可用度：**A = (1 − 公共开销) / (1 + ρ)**。公共开销是与故障无关的固定损耗，例如保存检查点。
- 模块可用度 Aᵢ = 1 / (1 + ρᵢ)，是只有该模块出故障时的系统可用度。
- 模块损失时间 = 窗口 × ρᵢ / (1 + ρ)。各模块之和加公共开销损失等于窗口 × (1 − A)。

这个式子在任何损失水平下都成立。原周度模型用“1 − 损失 / 窗口”，损失大时会算出负数。第 2 步的“可用度是怎么算出来的”把每个故障模式的 频次 × 单次损失 = 每周损失 列成一张表，再用四行算式合成系统可用度。

**差距。** 每个模块的现状与目标从三个角度对照：可用度；故障频次（MTBF 角度：现状每周几次，允许每周几次）；单次等效损失（MTTR 角度：现状多久，允许多久）。“频次 × 单次损失”图用双对数坐标画出每个模块的位置，等损失线是斜线：往左移是降频次，往下移是缩短单次损失。

### 分配：系统目标、两级分配

**系统目标随规模变化。** 故障次数与卡数成正比，所以与规模成正比的是损失负荷 r = 1/A − 1，而不是可用度本身：

A(N) = 1 / (1 + k·N)

k 是每张卡带来的损失负荷，代表一个可靠性水平。把给定的目标换算成“每万卡损失负荷”就能比较：10 万卡 99% 对应 1.01‰，50 万卡 95% 对应 1.05‰，两者几乎相同，是同一个单卡可靠性水平在不同规模下的体现。任务里保存一张“规模—目标”对照表，其它规模的目标按 k 对规模的对数插值，表外沿用端点的 k；改规模时目标跟着走，直接改目标等于给当前规模加一个目标点。

**后果大的模块单独指定目标。** 多数故障每周发生很多次、每次损失很小，窗口损失接近平均值，按平均损失分预算即可。少数事件一次就吃掉窗口预算的一大块（界面按 ≥ 1/3 列出），平均下来很小，可只要发生，这个窗口就不达标。对它们该约束的是“一个窗口内发生的概率” 1 − e^(−n)，所以目标单独指定，先从系统的损失负荷里扣除，不参与按权重分配。默认场景里机房供配电指定为 99.999%。界面给出建议值：把允许不达标的窗口比例拿出一半，平均分给这些模块，换算成允许的发生频次，再乘单次损失。

**其余模块按权重分配。** 由目标 A* 得到系统允许的损失负荷 ρ* = (1 − 公共开销) / A* − 1，扣除已指定的部分后按权重分给其余模块：ρᵢ* = wᵢ·(ρ\* − ρ指定)，Σwᵢ = 1，所以模块目标合成后恰好回到系统目标。

| 方法       | 权重               | 适用                                                                                           |
| ---------- | ------------------ | ---------------------------------------------------------------------------------------------- |
| AGREE      | wᵢ ∝ nᵢ / ωᵢ       | 有架构和器件清单的设计阶段。nᵢ 为复杂度（默认取固有失效率，也可取部件数量或手填），ωᵢ 为重要度 |
| ARINC 比例 | wᵢ ∝ 现状 ρᵢ       | 各模块改进难度相近，沿用现状结构                                                               |
| 等分配     | wᵢ = 1 / k         | 早期缺数据时的粗略起点                                                                         |
| 最小改进量 | ρᵢ\* = min(ρᵢ, ρ₀) | 把改进集中在损失最大的几个模块                                                                 |
| 自定义     | 手填               | 已有合同指标或上级分配                                                                         |

每个模块的预算给出两种等价的兑现方式：保持现状单次损失时每周故障 ≤ 某值（降频次），或保持现状频次时单次等效损失 ≤ 某值。

AGREE 不使用现状的恢复能力，所以它会把“故障不多但单次损失很大”的模块暴露出来。默认场景里 AICore 静默故障只有 67 FIT，却占了最大的一块损失，AGREE 下它超预算数百倍；ARINC 则会给它最大的预算。两种视角都有用，界面提供四种方法的并排对比。

### 设计：措施分层、收益与结论

**分层。** 每周损失 = 故障频次 × 单次等效损失，措施只有两个着力点：

- **组件级高可用**（类别：降低失效率）作用在频次上：AICore 静默故障压测筛查、HBM 纠错、下一代光模块、供电冗余等。对它针对的器件，后续所有环节等比例受益。
- **系统级可靠性机制**作用在单次损失上，按恢复链的先后分为四类：**检测**（检出率、检测时间、漏检后的兜底发现）、**恢复**（重执行、进程重调度、加快全局重启）、**隔离与弹性**（只影响故障域）、**检查点**（少回滚、低开销）。它们对多种器件的故障同时有效，但受故障类型限制。

措施改的是故障模式的参数：故障率、检出率、检测时间、漏检后发现时间、回滚重算、影响系数，以及恢复阶梯上某一级的成功率、耗时、失败耗时或影响范围。例如“进程重调度”把该级的成功率设为 95%、耗时 60 秒；“域级弹性恢复”把该级的成功率设为 98%、耗时 180 秒、影响范围 1/50。一项措施可以同时改几个参数，取值方式有三种：在现值上按比例降低、直接设为新值、在现值上增加（用于表达代价，例如校验带来的吞吐损失）。

每项措施有一个**适用比例**：所作用的故障中，措施实际适用并成功的比例，参数按它在现值与目标值之间折算。多项措施作用于同一参数时结果与顺序无关：多项“设为”只取改善最大的一项，不叠加；多项“降低”连乘（检出率的“降低”作用在漏检率上）；“增加”逐项累加。

**收益分析。**

- **改进程度—收益**：把一项措施的主要参数从现状（0）逐步推到理想极限（100%：故障率降到 0、检出率到 100%、时间缩到 0），其余措施保持不变，逐点重新评估。横轴是改进程度，纵轴是系统可用度提升的百分点；线的高度是这项措施的上限，计划点的位置说明现在的计划拿到了其中多少。
- **组合收益路径**：措施之间有重叠，单项收益不能直接相加。从现状出发，每一步加入“在已选措施基础上提升最大”的一项，得到一条累计可用度曲线和一个优先顺序；表中并列“单独做”和“排在这一步再提升”，两者的差就是相互作用。
- **贡献**按 Shapley 值分摊：对所有启用顺序求平均边际收益，各项之和恰好等于总提升。不超过 14 项时精确枚举，更多时用固定种子的排列抽样。
- **推荐方案**：在已启用措施的基础上，按数量从少到多穷举其余措施的组合，找到的第一组即数量最少；数量相同时优先证据更充分的，其次选可用度更高的。穷举不完时改为逐步加入提升最大的措施，达标后再剔除可以去掉的项，界面会注明不保证数量最少。措施库用尽仍不够时，按 ρ 与 ρ\* 的比值给出还需整体降低的比例。
- **参数反推**：其余措施不变，用二分法求某个参数取多少刚好达标。

**结论表**列出重点做的措施（已启用的加上建议补充的），按 Shapley 贡献排优先级，每项给出：计划做到多少（参数从现值到计划值）、**最低要求**（其余各项按计划兑现时，这一项的效果至少兑现多少仍能达标，二分求得）、贡献和证据状态。最低要求越接近 100%，越没有打折的余地；“可作为余量”表示去掉它仍达标。最低要求是单项的下限，几项同时打折时不能各自都取下限。

### 验证：独立仿真

仿真不使用解析公式。故障按事件率随机到达，按检出率随机决定是否检出：检出时用检测时间，漏检时发现时间取指数分布。随后逐级走恢复阶梯：每一级按成功率随机决定成败，成功时耗时取指数分布（乘该级影响范围），需要回滚的再加一段均匀分布的回滚重算；失败则计入失败耗时并升到下一级。窗口结束时截断未完成的恢复。现状和设计后使用不同的随机数流，默认每次更换种子。

五项判定：

1. 仿真均值的 95% 置信区间下限不低于目标。
2. 达到目标的窗口比例不低于要求（默认 90%，可调）。
3. 仿真与解析结果的偏差在容差内（3 倍标准误与 0.5 个百分点中较大者）。
4. 各模块的仿真损失不超过第 1 步的分配预算。
5. 所选措施都标记为有实测证据。

前四项是数值判定。第五项不影响数值，但未满足时结论为“数值达标，仍有待确认项”：仿真只能证明参数成立时可以达标。

## 默认场景

50 万卡、168 小时窗口、目标 95%；规模—目标对照为 10 万卡 99%、50 万卡 95%。数值都是可编辑的场景输入，不代表厂商实测失效率。

- **架构**：5 个分组、12 个模块。计算（AICore、NPU 其余部分、HBM、节点与板级）；网络（IO Die 与 L1 互联、光模块、L2 / Leaf / Spine 与网卡）；存储；柜级供电与冷却、机房供配电、管理面；软件与未归因。每个模块对应架构图上的一处硬件。
- **故障模式**共 15 种：11 种中断、2 种静默、2 种亚健康。
  - 故障率取自 2026-11-12 周度用户场景：每卡 HBM＋NPU 合计 1700 FIT，各占全部故障 15%；光模块占 35%（单只 500 FIT，按每卡约 4 只折算）；静默故障占 1.4%，其中 AICore 占 85%，检出率 90%，漏检后 48 小时才被发现。
  - 其余 35% 的模块拆分，以及其中亚健康的份额，按 2026-10-14 基线故障库各对象的相对构成折算，属先验。
  - 亚健康不中断任务，只降速 5%；检测等待和漏检后的发现时间已按降速比例折算成等效停机时间。
  - **机房供配电是示例假设**：全系统固定 1 套，约 5 年发生 1 次全局掉电，需人工恢复 4 小时，没有现成数据来源。它的作用是演示“单次影响大的模块单独指定目标”：现状约 99.991%，指定目标 99.999%。
- **恢复链**取自现有评估模型的基线参数：95% 在 10 秒检出、其余 60 秒超时；现状的恢复阶梯只有两级，检查点全局恢复 180 秒、成功率 99%，失败白费 180 秒后转人工恢复 2 小时；回滚重算平均 150 秒；检查点周期 300 秒、保存 4 秒（公共开销 1.32%）。重执行、进程重调度、域级弹性恢复三级现状不可用，由措施引入。
- **措施库**共 30 项。组件级（降低失效率）7 项；系统级 23 项：检测 7、恢复 10、隔离与弹性 4、检查点 2。
  - 用户给出的 4 项，默认启用：HBM 纠错降 60%、AICore 静默压测筛查降 60%、光模块 500 → 50 FIT、静默检出率 90% → 95%。
  - 现有基础机制的其余 7 项：中断快速检测、亚健康快速检测、静默故障干净 step 恢复、通信与算子重执行、进程重调度、域级弹性恢复、更频繁的检查点。作用范围按基线故障库中各机制适用的故障对象映射。
  - 现有扩展机制库的 16 项（FP8 与 FP4 两条路径的静默检测合为一项，共 15 项）：链路透明恢复、网络绕行与降级运行、故障隔离与传播抑制、控制面异常下业务连续运行、预热进程、运行时初始化快照、异步检查点保存、无损检查点压缩、故障分类与恢复动作匹配、算子 ABFT 校验、网络端到端静默检测、在线压测与异常资源筛除、HCCL 通信域弹性重建、CANN 图准备与启动缓存等。
  - 本工作台补充的 4 项：漏检静默故障定期校验（设计假设）、内存故障预测与主动隔离、供电冗余与器件降额、机房双路市电与后备电源（后三项是示例，取值没有现成来源）。

扩展机制库中有几项没有给出适用比例或成功率（原库标注为待测）。这些措施的适用比例暂取 50%，FP8 / FP4 路径的份额未知、暂取 0，均在措施的依据里写明，需要按故障注入结果修改。重执行、进程重调度和域级弹性恢复的成功率（80%、95%、98%）取自基础机制的设计值，同样需要实测确认。

默认场景的解析结果：

| 状态                                 | 可用度 |
| ------------------------------------ | ------ |
| 现状                                 | 65.03% |
| 启用用户给出的 4 项措施              | 79.68% |
| 再启用推荐的 8 项                    | 95.36% |
| 按收益逐项叠加全部有提升的 25 项     | 96.99% |
| 30 项全部启用（含 5 项净收益为负的） | 95.88% |

现状 65.03% 与周度场景给出的参考值 60% 接近但不相同；差异来自其余 35% 故障的拆分和恢复链参数都是先验。现状每周约 315 次故障，单次等效损失约 10.9 分钟，每周损失 58.8 小时，允许 8.4 小时。失效率最高的是光模块、HBM、NPU；损失最大的却是 AICore（67 FIT，但漏检一次损失 48 小时以上），这类模块的问题在单次损失而不在频次。

用户给出的 4 项措施不足以达到 95%，主要差距在中断类故障的单次损失和静默故障的漏检分支。推荐补充的 8 项是：域级弹性恢复、漏检静默故障定期校验、更频繁的检查点、故障分类与恢复动作匹配、异步检查点保存、链路透明恢复、算子 ABFT 实时矩阵校验、中断快速检测。候选有 26 项，这一组是逐步选取的结果，不保证数量最少。12 项合计提升 30.33 个百分点，其中组件级 3 项贡献 6.83、系统级 9 项贡献 23.50；贡献最大的是域级弹性恢复（6.24）、光模块可靠性提升（4.08）、漏检静默故障定期校验（3.68）。最低要求最紧的是域级弹性恢复（效果至少兑现 96%，即成功率不低于 94.1%）和光模块（至少兑现 86%，即不高于 112 FIT）；HBM 纠错和 AICore 压测筛查在这一组里可作为余量。

从现状出发按收益排序的组合路径，前三项是通信与算子重执行、算子 ABFT 实时矩阵校验、域级弹性恢复，三项合计 +20.80 个百分点；做到第 11 项达标。

**验证结果需要注意**：推荐方案的达标余量只有 0.36 个百分点。固定种子 20261117、2000 个窗口的独立仿真中，均值 95.43%（95% 区间 95.33%–95.52%），但达到目标的窗口只占 86.8%，低于默认 90% 的要求，结论是“未通过”。原因是静默故障漏检的长尾：平均值达标，但约七分之一的周会因为一次长时间漏检而不达标。要通过验证，需要再加措施留出余量，或进一步缩短漏检后的发现时间。

## 已知边界

- 故障按恒定失效率到达，不含早期失效和耗损期。
- 静默故障漏检后到被发现之间的时间按等效停机时间计入。实际是已完成的训练被作废，期间系统仍在运行并可能再出故障。
- 恢复阶梯假定各级成败相互独立，用到的最后一级必然成功；不模拟同一故障反复升级再降级。
- 规模—目标换算假定器件与机制水平不随规模变化；固定数量的设施（如机房供配电）不随规模增长，所以单独处理。
- 高后果模块的建议目标来自“允许不达标的窗口比例拿出一半平均分配”这一约定，是起点而非唯一答案。
- 不考虑多个故障同时发生时共享一次恢复，也不区分瞬态与永久故障的备件等待。
- 影响系数小于 1 的事件按等效停机时间计入。
- 置信区间只反映随机抽样误差，不含故障率与恢复参数本身的不确定性。
- 新模型与专家模式的事件库、六阶段记录相互独立，不自动同步。需要 54 类事件、检查点逐事件账本或专家引擎复现时，使用专家模式。

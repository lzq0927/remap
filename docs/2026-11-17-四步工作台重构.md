# 四步工作台重构

2026-11-17。本次把默认界面重构为一个四步工作台：**目标分配 → 可用度评估 → 机制设计 → 机制验证**。四步共用一份模型和一套公式，每一步只有一页。原有界面完整保留为“专家模式”。

2026-11-24 补充了分析逻辑：目标随规模变化、后果大的模块单独指定目标、以周为粒度的频次与单次损失差距、从小到大的恢复链、措施分层，以及改进程度收益、组合收益路径和“重点做哪几项、做到什么程度”的结论。同日按用户给出的现有恢复措施与预计改进更新了默认场景，恢复链改为“进程重调度 → 弹性恢复 → CKPT 回滚 → 人工”的走法，并增加各环节耗时的横向条形图。下文按更新后的口径描述。

## 分析主线

整套分析围绕一个恒等式展开：

**每周损失 = 故障频次 × 单次等效损失**

| 步骤       | 回答的问题                 | 方法                                                                                 |
| ---------- | -------------------------- | ------------------------------------------------------------------------------------ |
| 目标分配   | 每个模块允许损失多少       | 系统目标随规模换算；后果大的模块单独指定；其余按 AGREE 等方法分配                    |
| 可用度评估 | 现在损失多少、差在哪       | 频次来自器件失效率，单次损失来自检测与恢复阶梯；差距分别从频次和单次损失两个角度给出 |
| 机制设计   | 做哪几项措施、做到什么程度 | 组件级措施降频次，系统级措施缩短单次损失；看改进程度收益、组合收益路径、Shapley 贡献 |
| 机制验证   | 结论在随机波动下是否成立   | 独立的离散事件仿真，逐级模拟恢复阶梯                                                 |

## 为什么重构

原任务页把周度场景、四部分流程、架构图谱、事件库、分配编辑、分析工作台等内容叠在同一页，一屏约 6600 像素，重点不清。更根本的问题是数据分散：周度模型、审核事件库和 AGREE 分配各有一套输入，改一处参数不能直接看到对目标差距的影响。

重构后的原则：

1. **一份模型。** 架构模块 → 故障模式 → 可靠性措施。四步都只读写它。
2. **一套口径。** 分配、评估、设计都在“损失负荷 ρ”上进行，结果可以直接比较、相加和闭合。
3. **一步一页。** 每页先给结论，再给明细；方法说明默认收起。
4. **参数都可调。** 规模、窗口、目标、每个模块的故障率与恢复参数、每项措施的取值都能改，改后即时重算并自动保存。

## 方法

### 评估：频次、恢复链与系统可用度

训练任务是串联系统，任何模块故障都会打断任务；任务停机时不产生新故障。

**故障频次。** λᵢ = FITᵢ × 部件总数 / 10⁹（次 / 运行小时）。按卡计的模块，部件总数 = 每卡数量 × 卡数；机房供配电这类全系统只有固定几套的设施，部件总数不随规模变化。界面显示的故障频次是“每连续运行一周（168 小时）发生的次数”，等于 168 ÷ MTBF，只由失效率和数量决定；每周不到 1 次的写成“每年几次”或“几年 1 次”。日历周里实际发生的次数还要乘运行时间占比 1 / (1 + ρ)，现状停机多时两者差别很大，所以对照目标时用前者。

**单次等效损失。** 一次故障的损失由检测和恢复链决定：

1. 检测：以概率 c 被检出，耗时 t检出；否则漏检，过 t发现 之后才被兜底手段发现（静默故障是定期校验或结果异常，中断故障是超时）。
2. 恢复链：级别从小到大排列，每一级有自己的走向。

| 级别       | 含义                                   | 成功后         | 失败后   |
| ---------- | -------------------------------------- | -------------- | -------- |
| 就地恢复   | 原地重执行、绕行或快照降载，任务不回滚 | 恢复           | 走下一级 |
| 进程重调度 | 只重新调度出错的进程                   | 恢复           | 走下一级 |
| 弹性恢复   | 隔离并替换故障资源，重建通信域         | 再走 CKPT 回滚 | 转人工   |
| CKPT 回滚  | 从最近的检查点恢复并重算               | 恢复           | 转人工   |
| 人工恢复   | 自动手段都失败后由人处理               | 恢复           | —        |

即：进程重调度成功即恢复，失败走弹性恢复；弹性恢复成功后再走 CKPT 回滚，失败转人工；CKPT 回滚失败也转人工。走向（成功后恢复还是再走下一级、失败后走下一级还是转人工）是每个故障模式每一级的可编辑属性，上表是默认场景的取法。

每一级有成功率 pₖ、成功耗时 tₖ、失败白费的时间 fₖ、影响范围 κₖ。成功率为 0 的级别默认跳过；标为“必经”的级别即使成功率为 0 也留在链上，按失败处理，用来表达“这一步绕不开，但现在还不具备”。失败后无处可去的级别按必定成功计算。

MTTRᵢ = κ · [ c·t检出 + (1 − c)·t发现 + Σₖ 到达ₖ·(pₖ·tₖ + (1 − pₖ)·fₖ)·κₖ + Σ恢复于第 k 级且需回滚 结束ₖ·t回滚 ]

到达ₖ 是走到第 k 级的概率，沿走向逐级推出（所有走向都朝粒度更大的方向，按顺序算一遍即可）；回滚重算只在最终恢复的那一级计一次。CKPT 回滚一次的耗时 ≈ 恢复时间 + 保存间隔的一半。

第 2 步对每个故障模式给出四种视图，并与措施生效后的结果并排：

- **恢复链图**：故障发生 → 检测 → 各级，标出成功率、耗时、到达概率，成功与失败各走向哪里，在哪一级恢复。
- **各环节耗时**（横向堆叠条）：每一段是一个环节的期望耗时（概率 × 时间），整条的长度就是单次等效损失，一条线看出时间花在哪一块。现状与设计后可以各自撑满（看构成），也可以用同一时间尺度（比长短）。
- **按路径看**：每一行是一种可能的经过（例如“进程重调度失败 → 弹性恢复 → CKPT 回滚”），条的长度是这条路径实际花的时间，左边是走到它的概率，浅色段是失败白费的时间。各行“概率 × 时间”相加等于单次等效损失。
- **逐环对比表**，以及“这一级值多少”：把某一级拿掉后单次等效损失增加多少。结果为负的级别，是成功率太低或耗时太长，先试它反而比直接走后面的级别更慢。

**系统可用度。**

- 损失负荷：ρ = Σ λᵢ·MTTRᵢ，含义是每运行 1 小时平均损失多少小时。ρ 对故障模式和模块可加。
- 系统可用度：**A = (1 − 公共开销) / (1 + ρ)**。公共开销是与故障无关的固定损耗，例如保存检查点。
- 模块可用度 Aᵢ = 1 / (1 + ρᵢ)，是只有该模块出故障时的系统可用度。
- 模块损失时间 = 窗口 × ρᵢ / (1 + ρ)。各模块之和加公共开销损失等于窗口 × (1 − A)。

这个式子在任何损失水平下都成立。原周度模型用“1 − 损失 / 窗口”，损失大时会算出负数。第 2 步的“可用度是怎么算出来的”把每个故障模式的 故障频次 × 单次损失 ÷ 168 = 损失负荷 列成一张表，再用四行算式合成系统可用度。

**差距。** 每个模块的现状与目标从三个角度对照：可用度；故障频次（MTBF 角度）；单次等效损失（MTTR 角度）。“优先方向”看措施库里哪一边能补得更多：只用全部系统级措施能把这个模块的损失降多少，只用全部组件级措施能降多少。“频次 × 单次损失”图用双对数坐标画出每个模块的位置，等损失线是斜线：往左移是降频次，往下移是缩短单次损失。

### 分配：系统目标、两级分配

**系统目标随规模变化。** 故障次数与卡数成正比，所以与规模成正比的是损失负荷 r = 1/A − 1，而不是可用度本身：

A(N) = 1 / (1 + k·N)

k 是每张卡带来的损失负荷，代表一个可靠性水平。把给定的目标换算成“每万卡损失负荷”就能比较：10 万卡 99% 对应 1.01‰，50 万卡 95% 对应 1.05‰，两者几乎相同，是同一个单卡可靠性水平在不同规模下的体现。任务里保存一张“规模—目标”对照表，其它规模的目标按 k 对规模的对数插值，表外沿用端点的 k；改规模时目标跟着走，直接改目标等于给当前规模加一个目标点。

**后果大的模块单独指定目标。** 多数故障每周发生很多次、每次损失很小，窗口损失接近平均值，按平均损失分预算即可。少数事件发生得少（每个窗口不到 3 次），但一次就吃掉窗口预算的一大块（界面按 ≥ 1/3 列出），平均下来很小，可只要发生，这个窗口就不达标。对它们该约束的是“一个窗口内发生的概率” 1 − e^(−n)，所以目标单独指定，先从系统的损失负荷里扣除，不参与按权重分配。默认场景里机房供配电指定为 99.999%。恢复能力按当前设计计：例如人工恢复 4 小时本身也超过周预算的三分之一，启用把它缩到 1 小时的措施后才不再列入。界面给出建议值：把允许不达标的窗口比例拿出一半，平均分给这些模块，换算成允许的发生频次，再乘单次损失。

**其余模块按权重分配。** 由目标 A* 得到系统允许的损失负荷 ρ* = (1 − 公共开销) / A* − 1，扣除已指定的部分后按权重分给其余模块：ρᵢ* = wᵢ·(ρ\* − ρ指定)，Σwᵢ = 1，所以模块目标合成后恰好回到系统目标。

| 方法       | 权重               | 适用                                                                                           |
| ---------- | ------------------ | ---------------------------------------------------------------------------------------------- |
| AGREE      | wᵢ ∝ nᵢ / ωᵢ       | 有架构和器件清单的设计阶段。nᵢ 为复杂度（默认取固有失效率，也可取部件数量或手填），ωᵢ 为重要度 |
| ARINC 比例 | wᵢ ∝ 现状 ρᵢ       | 各模块改进难度相近，沿用现状结构                                                               |
| 等分配     | wᵢ = 1 / k         | 早期缺数据时的粗略起点                                                                         |
| 最小改进量 | ρᵢ\* = min(ρᵢ, ρ₀) | 把改进集中在损失最大的几个模块                                                                 |
| 自定义     | 手填               | 已有合同指标或上级分配                                                                         |

每个模块的预算给出两种等价的兑现方式：保持现状单次损失时故障频次（每连续运行一周）≤ 某值，或保持现状频次时单次等效损失 ≤ 某值。

AGREE 不使用现状的恢复能力，所以它会把“故障不多但单次损失很大”的模块暴露出来。默认场景里 AICore 静默故障只有 67 FIT，单次等效损失却是其他模块的 3 倍，AGREE 下它超预算的倍数最高；ARINC 则按现状占比给预算。两种视角都有用，界面提供四种方法的并排对比。

### 设计：措施分层、收益与结论

**分层。** 每周损失 = 故障频次 × 单次等效损失，措施只有两个着力点：

- **组件级高可用**（类别：降低失效率）作用在频次上：AICore 静默故障压测筛查、HBM 纠错、下一代光模块、供电冗余等。对它针对的器件，后续所有环节等比例受益。
- **系统级可靠性机制**作用在单次损失上，按恢复链的先后分为四类：**检测**（检出率、检测时间、漏检后的兜底发现）、**恢复**（就地恢复、进程重调度、CKPT 回滚、人工恢复）、**隔离与弹性**（隔离并替换故障资源）、**检查点**（少回滚、低开销）。它们对多种器件的故障同时有效，但受故障类型限制。

措施改的是故障模式的参数：故障率、检出率、检测时间、漏检后发现时间、回滚重算、影响系数，以及恢复链上某一级的成功率、耗时、失败耗时或影响范围。例如“弹性恢复”把该级的成功率从 0 设为 0.99、耗时 60 秒；“智能故障管理 Agent”把人工恢复的耗时从 4 小时设为 1 小时。一项措施可以同时改几个参数，取值方式有三种：在现值上按比例降低、直接设为新值、在现值上增加（用于表达代价，例如校验带来的吞吐损失）。

每项措施有一个**适用比例**：所作用的故障中，措施实际适用并成功的比例，参数按它在现值与目标值之间折算。多项措施作用于同一参数时结果与顺序无关：多项“设为”只取改善最大的一项，不叠加；多项“降低”连乘（检出率的“降低”作用在漏检率上）；“增加”逐项累加。

**收益分析。**

- **各措施值多少**：一项措施的收益 = 有它和没有它时系统可用度之差，其余措施保持当前的启用状态。每项给两个数：按计划参数做到的收益，以及把主要参数推到理想极限（故障率降到 0、成功率或检出率到 100%、时间缩到 0）的收益。界面用一排横条表示：实心是计划收益，后面的浅色是做到极限还能多拿的部分。
- **参数—收益曲线**：展开任一措施，可以逐个参数看“取值—系统可用度”曲线：这一个参数从不改一路扫到理想极限，其余参数停在计划值、其余措施不动。拖动滑块试算任意取值，满意后采用。措施的“改进前”（现状参数）和“改进后”都可以直接修改；改进前各故障模式取值不同时逐个模式修改。
- **组合收益路径**：措施之间有重叠，单项收益不能直接相加。从现状出发，每一步加入“在已选措施基础上提升最大”的一项，画成瀑布：每一行是加入的措施、可用度从哪里到哪里、这一步提升多少。某一步的收益和“单独做”差得明显时，指出是前面哪一项造成的（把那一项从前序措施里拿掉，这一步的收益往回变得最多的就是它）：收益变小是两者省的同一段损失，收益变大是前一项让更多故障走到这一步改进的环节，或削掉了别的损失。
- **暂不优化**：措施可以标为“暂不优化”，表示这项机制先保持现状。它不进入推荐方案、组合路径和“各方向能补多少”的估算，启用后即视为纳入设计。推荐方案不达标时，同时给出剩余故障损失花在哪个环节（检测、漏检后发现、恢复链各级、回滚重算），指出该从哪一级的参数下手。
- **贡献**按 Shapley 值分摊：对所有启用顺序求平均边际收益，各项之和恰好等于总提升。不超过 14 项时精确枚举，更多时用固定种子的排列抽样。每项同时列出“单独做”（只上这一项）和“最后加”（其余都已启用后再加它）；同一项措施的单独做、组合路径里的增量和分摊值是三个不同的数，分摊值介于前两者之间。
- **推荐方案**：在已启用措施的基础上，按数量从少到多穷举其余措施的组合，找到的第一组即数量最少；数量相同时优先证据更充分的，其次选可用度更高的。穷举不完时改为逐步加入提升最大的措施，达标后再剔除可以去掉的项，界面会注明不保证数量最少。措施库用尽仍不够时，按 ρ 与 ρ\* 的比值给出还需整体降低的比例。
- **参数反推**：其余措施不变，用二分法求某个参数取多少刚好达标。

**结论表**列出重点做的措施（已启用的加上建议补充的），按 Shapley 贡献排优先级，每项给出：计划做到多少（参数从现值到计划值）、**最低要求**（其余各项按计划兑现时，这一项的效果至少兑现多少仍能达标，二分求得）、贡献和证据状态。最低要求越接近 100%，越没有打折的余地；“可作为余量”表示去掉它仍达标。最低要求是单项的下限，几项同时打折时不能各自都取下限。

### 验证：独立仿真

仿真不使用解析公式。故障按事件率随机到达，按检出率随机决定是否检出：检出时用检测时间，漏检时发现时间取指数分布。随后按恢复链的走向逐级走：每一级按成功率随机决定成败，成功时耗时取指数分布（乘该级影响范围），然后或者恢复（需要回滚的再加一段均匀分布的回滚重算），或者再走下一级；失败则计入失败耗时，走下一级或转人工。窗口结束时截断未完成的恢复。现状和设计后使用不同的随机数流，默认每次更换种子。

五项判定：

1. 仿真均值的 95% 置信区间下限不低于目标。
2. 达到目标的窗口比例不低于要求（默认 90%，可调）。
3. 仿真与解析结果的偏差在容差内（3 倍标准误与 0.5 个百分点中较大者）。
4. 各模块的仿真损失不超过第 1 步的分配预算。
5. 所选措施都标记为有实测证据。

前四项是数值判定。第五项不影响数值，但未满足时结论为“数值达标，仍有待确认项”：仿真只能证明参数成立时可以达标。

默认场景的解析结果：

| 状态                                                                                        | 可用度 | MTBF       | 单次等效损失（MTTR） |
| ------------------------------------------------------------------------------------------- | ------ | ---------- | -------------------- |
| 现状                                                                                        | 45.13% | 17 分钟    | 20.4 分钟            |
| 只改进光模块                                                                                |        | 36 分钟    |                      |
| 默认启用的 7 项（含 HBM 纠错）                                                              | 74.58% | 44.48 分钟 | 15.1 分钟            |
| 措施库里其余有提升的措施全部做足（进程重调度不优化）                                        | 92.40% |            |                      |
| 7 项 + 进程重调度做到 0.95 / 60 秒 + 算子 ABFT 实时矩阵校验 + 漏检静默故障定期校验（10 项） | 95.12% | 44.48 分钟 | 2.2 分钟             |

几点结论：

- **两项降失效率措施把 MTBF 从 17 分钟提到 44.5 分钟**：光模块 3775 → 50 FIT，单这一项到 36 分钟；HBM 再少 635 FIT，到 44.48 分钟。每卡 FIT 从 7059 降到 2698，光模块在剩余故障里的占比降到 1.9%，每连续运行一周的故障次数从 593 次降到 227 次。
- **到 95% 允许的单次等效损失约 2.3 分钟**：A = (1 − 开销) / (1 + MTTR / MTBF)，MTBF 44.48 分钟、公共开销 0.08% 时，MTTR ≤ 2.30 分钟（不计开销是 2.34 分钟）。默认 7 项之后是 15.1 分钟，还要缩到原来的约七分之一。
- **现状的损失花在哪**：CKPT 回滚 34%、静默漏检后的发现时间 20%、进程重调度 19%、回滚重算 17%、人工恢复 8%。默认 7 项之后，静默漏检后的发现时间升到 35%，进程重调度 25%、CKPT 回滚 23%。
- **弹性恢复按现在给的参数是负收益**（在默认 7 项里的分摊贡献 −2.14 个百分点）：现状已经是“进程重调度失败 → CKPT 回滚”，加上弹性恢复后变成先花 60 秒弹性恢复再回滚，并多出 1% 失败转人工的分支。它的价值（例如让回滚不必等故障资源修复、提高回滚成功率）没有体现在现有参数里，需要补充现状下 CKPT 回滚在硬件故障时的成功率或等待时间。
- **进程重调度不优化，到不了 95%**：其余有提升的措施全部做足只到 92.40%，那时剩余损失的 43% 花在进程重调度、38% 花在 CKPT 回滚。把它做到设计目标 0.95 / 60 秒，再加算子 ABFT 实时矩阵校验和漏检静默故障定期校验，共 10 项，到 95.12%；其中进程重调度贡献 22.4 个百分点，几乎没有打折余地（效果至少兑现 99%）。
- 同一套参数放到 10 万卡（目标 99%）：现状 80.09%，默认 7 项 93.55%，上面的 10 项 98.83%。

**验证结果需要注意**：10 项方案的余量只有 0.1 个百分点。固定种子 20261126、4000 个窗口的独立仿真中，均值 95.11%（95% 区间 95.02%–95.21%），但达到目标的窗口只占 79.7%，低于默认 90% 的要求，结论是“未通过”。均值刚过线时，约五分之一的周会因为一次长时间的静默漏检而不达标；要通过验证，需要再加措施留出余量。

## 与 2026-11-19 约束研究的合并

主干上另有一条 2026-11-19 的研究线（[固定域约束与五规模收益](2026-11-19-固定域约束与五规模收益.md)、[恢复收益审计与 MTBF 独立对照](2026-11-19-恢复收益审计与MTBF独立对照.md)），它在当时的模型（单一恢复时间、漏检分支总损失、措施分“提升 MTBF / 降低 MTTR”）上增加了域级要求、五规模对比和措施审计。2026-11-25 把两条线合并，以恢复链模型为底：

- **两种固定目标并存。** 域级要求（`requirements`，可选）给一组模块合起来定目标，例如网络域 98%、供电与冷却 99.999%；模块上的“单独指定目标”给单个模块定目标。分配时两者都先从系统预算里扣除，域内再按所选方法分给各模块；模块落在某个固定域里时，它自己的指定目标不再单独生效。
- **两种规模换算并存。** 有域级要求时，系统目标按参考规模折算：固定公共开销单独留出，故障损失负荷随卡数线性变化，A*(N) = (1 − o) / (1 + ρ*·N / N₀)。没有域级要求时，用“规模—目标”对照（见上文）。两者的区别在公共开销是否单独处理。
- **“从现状减少”的参数变化。** 措施的取值方式增加一种：相对冻结的现状减少一个绝对量，用于“某个阶段省 45 秒”这类阶段节省。它与“设为”按替代方案取最好的一项，不会抹掉校准后的其余恢复时间，也不重复扣减。默认措施库里五项启动阶段的节省（运行时初始化快照、预热进程、HCCL 重建、CANN 图缓存、无损检查点压缩）改用这种方式。
- **约束研究场景冻结保存。** 第 1 步底部可以载入 2026-11-19 的约束场景。它以当时的默认参数为底（冻结在 `packages/core/src/legacy-november.ts`），读入时升级为恢复链结构，不随当前默认场景变化；与本文的默认场景是两套独立的输入。按域现状反求恢复时长时，缩放的是中断类故障恢复链上各级的耗时。
- **界面。** 有域级要求的任务：第 1 步顶部显示域级要求表（代替“规模与目标”卡片），架构图上方显示各域的现状与目标，第 3 步显示逐措施的五规模收益曲线，第 4 步增加五规模和各固定域的独立仿真。其它任务里，五规模收益曲线收在第 3 步的折叠区里。差距表按“超出预算的每周小时”排序；架构图上标每周损失和连续运行一周的故障频次，底色按每周损失的固定色尺由浅蓝到红。

## 已知边界

- 故障按恒定失效率到达，不含早期失效和耗损期。
- 静默故障漏检后到被发现之间的时间按等效停机时间计入。实际是已完成的训练被作废，期间系统仍在运行并可能再出故障。
- 恢复链假定各级成败相互独立，失败后无处可去的级别必然成功；走向只朝粒度更大的方向，不模拟同一故障反复升级再降级。
- 弹性恢复按给定的粗粒度参数建模（成功率、耗时），没有体现它对影响范围和后续 CKPT 恢复时间的改善。
- 规模—目标换算假定器件与机制水平不随规模变化；固定数量的设施（如机房供配电）不随规模增长，所以单独处理。
- 高后果模块的建议目标来自“允许不达标的窗口比例拿出一半平均分配”这一约定，是起点而非唯一答案。
- 不考虑多个故障同时发生时共享一次恢复，也不区分瞬态与永久故障的备件等待。
- 影响系数小于 1 的事件按等效停机时间计入。
- 置信区间只反映随机抽样误差，不含故障率与恢复参数本身的不确定性。
- 新模型与专家模式的事件库、六阶段记录相互独立，不自动同步。需要 54 类事件、检查点逐事件账本或专家引擎复现时，使用专家模式。

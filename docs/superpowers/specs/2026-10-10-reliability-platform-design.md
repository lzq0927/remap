# 统一可靠性建模评估验证系统：总体设计

日期：2026-10-10。状态：需求与总体设计已确认；用户在指标和资产库补充后确认“需求已清晰”。本文作为实施计划依据，不代表软件已实现或验证。

本文将已确认需求与推荐设计分开。阶段顺序依据能力依赖，允许提前交付，不按月底节点放缓开发。详细任务、技术版本与代码目录在设计确认后写入实施计划。

## 1. 已确认的产品目标

建设支持不同产品的可靠性设计决策系统。首期以 AI 训练集群为主场景，通过整体目标分解、机制评估和验证，回答“当前方案能否达标、差距在哪里、如何改进、依据是什么”。

产品“可用度”在训练场景下指正确有效产出率，建议显示为“训练有效可用度”。它不同于运行可用度、任务无故障概率或输出正确率；内部使用独立指标标识，避免同名混算。

设评估窗口为 T，主指标定义为：

单条轨迹：`A_delivery(T) = P_correct(T) × I_clean_end(T) / W_ideal(T)`。

其中 `P_correct` 是按理想吞吐归一化后的正确净进度，`W_ideal` 使用同一工作量单位；`I_clean_end` 表示期末不存在未恢复静默污染。若用等效理想训练小时计量，720 小时窗口的分母为 720。首期显示名为“训练有效可用度（正确交付产出率）”，内部指标为 `training.correct_delivery_ratio`，下文的 `A_effective` 均指该交付指标。

用户指定以根目录 `正确有效产出改进分析.html` 为基准。其明确判据是：期末仍有未恢复静默污染时，该轨迹的交付产出为 0；污染在期末前恢复后，按剩余正确净进度计分。损失账本包括错误计算损失和污染终态导致其他正确进度判废，二者不得重复扣减。未污染但进度较少仍按实际进度计分，不等同于固定工作量完成概率。

指定 HTML 同时返回 `effective=correct/T`、`uptime=uptime/T` 和 `delivery=delivered/T`，但图表与 Shapley 实际使用 `delivery`；不能因为变量名为 effective 就误选指标。

交付判据作为版本化策略记录。根目录 V4 的“污染终态交付归零”与 `catalogs/review-2026-10-09` 的“保留最后干净检查点”是不同策略，首期默认对齐前者。后者可作为明确命名的另一个场景，比较时必须标出判据变化，不能将其当作机制改进收益。

首期按 `E[A_effective(T)] ≥ 产品目标` 评价平均达标，同时报告结果分布和 `P(A_effective(T) ≥ 产品目标)`。可配置附加概率要求。参数不确定性、Monte Carlo 均值估计误差与单次任务随机波动分别呈现。

用户给出的目标示例：万卡 99%，十万卡 94.3%；相关 MTBF 示例为 31.5 小时和约 3 小时。系统分别存储目标与参数，不把这些数值硬编码为换算公式。不同规模的目标由明确目标表或经过确认的规则给出。

同一规模和指标口径下，同代际不同方案及跨代际方案接受相同目标约束。每个方案记录其理想吞吐基准；同时报告绝对正确产出及资源代价，避免相同比例掩盖跨代际实际产出差异。方案比较前检查工作负载、训练质量要求、窗口、目标和基准定义是否可比。

## 2. 实现路径比较与推荐

| 路径 | 优点 | 代价与限制 |
|---|---|---|
| 通用核心＋场景包＋工具适配器（推荐） | 可沉淀领域资产，替换 Agent，逐步扩展产品；首个场景能完整验证架构 | 首先需要明确模型与接口契约 |
| 直接在专家仓库上扩展界面与 Agent | 训练案例接入较快，易保留已有行为 | 单作业、固定参数与报告组织容易渗入通用系统，后续拆分成本高 |
| 一次建设全部产品与完整工具平台 | 产品覆盖面广 | 缺少多产品真实数据与验证条件，容易出现大量未经验证的模型 |

推荐第一条。首版采用模块化应用和独立求解进程；通过明确包边界实现解耦，暂不引入微服务集群。专家模型通过适配器作为训练内核候选和回归基准接入。

## 3. 完整用户流程

1. 用户进入项目，选择产品类别与场景；Agent 通过 `/sd-dfr-remap` 加载工作流。
2. 确认产品规模、目标、指标定义、评估窗口、工作负载和要支持的设计决策。
3. 导入架构图、设备与故障模式表、机制说明及参数材料；获得有来源关联的结构化草稿。
4. 确认关键歧义、系统依赖、故障传播、影响域和参数假设。
5. 系统建议方法、粒度和指标分配策略；用户可调整，并选择多方法对比。
6. 检查目标上界与可行性，生成子系统/组件预算及机制要求。
7. 计算基线，评估候选机制与组合，展示风险、损失、收益、代价和达标差距。
8. 按敏感性和差距调整设计或细化模型，重新求解并保存版本。
9. 执行实现检查、交叉校验及可获得的现实验证，输出报告和可追溯资产包。

每一步均有独立输入、输出、校验结果和运行状态。流程可暂停、修改、恢复；不能以聊天记录替代已确认的系统事实。

## 4. 模块与解耦边界

| 模块 | 职责与输入输出 | 独立性要求 |
|---|---|---|
| LUI | 展示资产、过程、图形、结果和会话；发起用户操作 | 不直接实现可靠性公式，不依赖 OpenCode 内部数据结构 |
| Agent 适配层 | 映射会话、消息、流式事件、工具请求和交互确认 | 首接 OpenCode，替换时不改领域模型或求解器 |
| Skill 包 | 编排领域步骤，解释方法选择，调用专业工具 | 核心内容为可移植 SKILL.md 和配套资源；平台命令入口单独适配 |
| 工作流与实验服务 | 保存步骤状态、版本、依赖、任务队列与运行记录 | 脱离 LLM 仍可检查状态、重放求解和导出报告 |
| 领域模型与场景包 | 描述目标、结构、故障、传播、机制、指标和参数 | 通用字段与训练专属字段分离；场景包提供默认值、校验和推荐规则 |
| 专业工具 | 分配、求解、对比、敏感性、验证等确定性计算或随机仿真 | 核心库可由测试/CLI 独立调用，MCP 作为协议适配层 |
| 资产与证据存储 | 保存源文件快照、结构化版本、参数证据、结果和报告 | 稳定 ID、版本及内容摘要；导出后能迁移到公司 Agent 平台 |

OpenCode 会话事件经适配层传给界面，领域工具运行事件经实验服务传给界面，两者通过 run_id、step_id 和 artifact_id 关联。工具计算和资产操作不依赖模型自由文本中的特定格式。

公开文档存在不同 OpenCode 版本的配置差异，实施时锁定版本并用最小集成实验验证 command、Skill、MCP 和服务接口的组合，不混用配置。

## 5. 领域资产契约

统一资产包括：评估任务、指标定义、目标配置、系统模型、故障事件、机制策略、参数证据、分配方案、实验配置、运行结果、验证证据和报告。

关键约束：

- 系统包含组件层级和依赖图；业务层、网络层、硬件层是默认视图，允许其他分层和跨层依赖。
- 每个故障分别记录来源、模式、触发/到达过程、暴露口径、表现、传播关系及影响范围。
- 设备 FIT、作业中断率、软件每调用/每任务失败概率分别表示。组件数量、单位和根因去重规则明确，防止重复累计。
- 机制记录覆盖对象、触发条件、检测、定位、隔离、恢复、验证、重新加入及失败回退。成功率、时间分布、资源开销和前置依赖显式表示。
- 参数记录数值或分布、单位、来源定位、版本、适用条件、证据等级和估计方法；缺失值不自动替换为零或理想能力。
- 参数变化、结构变化、模型升级均创建新版本；已完成结果始终绑定旧输入快照。
- 工作流轨迹记录决策、输入输出资产、工具版本、随机种子、错误和用户反馈；不要求保存模型隐藏推理。

### 5.1 系统必须维护的知识与资产库

故障模式库和可靠性机制库属于首期正式功能，支持独立维护，不只是一次评估的导入附件。

| 库 | 主要内容 | 与评估的关系 |
|---|---|---|
| 故障模式库 | 稳定 ID、组件/软件类型、模式、发生条件、表现、传播与影响范围、适用产品/代际、证据及验证状态 | 按场景实例化故障源；FIT 或每任务失败概率来自匹配条件的参数条目，不作为跨产品通用常数 |
| 可靠性机制库 | 稳定 ID、检测/隔离/恢复类别、覆盖模式、能力与版本、触发/前置条件、互斥与依赖、成功率及耗时、失败回退、资源和性能开销 | 一项机制可覆盖多个模式，同一模式可由机制链或组合处理；求解时验证可行性和覆盖关系 |
| 参数与证据库 | FIT、暴露口径、概率、时延分布、性能曲线、采样量、数据来源、设备/软件版本与环境 | 为模式和机制提供条件化参数；明确先验、假设、实测估计及不确定性 |
| 模型与场景模板库 | 架构/工作负载模板、指标及交付判据、分配方法配置、求解器适用范围 | 用于不同产品和代际的实例化，训练专属配置不侵入通用模型 |
| 验证案例库 | 解析基准、确定性故障序列、专家基线、注入/历史回放材料及预期结果 | 支撑工具、机制和模型升级回归，记录已验证范围 |

独立维护真实故障事件台账：事件是某时刻实际发生的一次记录，模式是可复用的分类和行为定义。事件通过模式 ID、设备/作业、根因 ID 和证据关联，去重后用于估计参数，不能将告警数量直接当故障次数。

所有库提供检索/筛选、新增、编辑、复制为新版本、批量导入导出、差异对比、校验、发布和弃用。生命周期为草稿、已校验、已发布、已弃用；已发布版本不可原地覆盖。被实验引用的条目不得物理删除，只能弃用并保留历史可读性。

公共库与项目实例分开：项目引用指定版本并允许显式局部覆盖，记录覆盖原因；公共库更新时提示受影响项目，不自动修改历史模型或结果。每个实验保存所引用条目及参数的完整快照，报告可追溯。

Agent 通过 MCP 检索和提出结构化变更，领域服务校验后写入草稿；发布为可复用条目必须经过验证并由用户确认。无法确认的图文解析结果、推测故障和理想机制能力不得自动成为已发布事实。

首批验收包括：新增一个故障模式及对应机制、关联证据、建立覆盖关系、实例化到训练场景、运行并查看贡献；更新库版本后旧报告结果不变，新场景可选择升级并展示差异。

## 6. 指标分解与达标闭环

整体目标先转换为允许损失预算，例如 99% 对应总损失不超过理想产出的 1%。按可核对的损失账本拆分到停机、保存、降速、局部容量损失、回退与未恢复错误等项，再映射到子系统/组件和机制参数。

此过程不是把 1% 随意平分，也不是将各子系统有效产出率直接相乘。联合故障、共享依赖和机制交互通过完整模型回算。

提供方法注册表，声明输入、输出、公式版本、适用条件、假设、校验规则及已验证范围：

| 方法 | 用途与限制 |
|---|---|
| Availability 串联合成＋预算权重 | 对满足独立串联条件的运行可用度子模型合成和分配；用于训练模型中的适用子问题 |
| Equal | 对明确的失效率、对数可靠度或指定损失预算均分，作为解释性基线 |
| ARINC | 在符合传统假设的子模型中按基线失效率比例分配，不直接对训练产出率套公式 |
| AGREE | 按复杂度、重要度和工作时长分配，显示采用的公式及近似边界 |
| 模型约束搜索 | 在机制依赖、参数上下限、成本及目标约束下生成可行组合，再由求解器检验 |

系统推荐时先检查适用性与数据充分性，再考虑计算成本。用户可以选择多个适用方法同时运行；不适用的方法显示原因及所需补充条件。

分配结果包括：对象、分配指标及目标、当前值、差距、可调整变量、推荐机制、来源方法、假设及正向验证结果。无法达标时输出约束冲突与主要限制；区分“在已声明模型内证明不可行”和“在当前搜索范围内未找到可行方案”。

预算分配、损失记账与 Shapley 归因分别实现。Shapley 分配的是约定组合下的收益，不是预算最优解或真实世界因果证明。缺少可信成本时只报告收益和工程约束，不虚构成本最优方案。

## 7. 求解器体系与首期训练模型

首个闭环采用单个训练作业、可配置规模与时间窗口，对齐专家案例；多作业调度作为后续场景扩展。

首个闭环纳入中断、亚健康、静默错误、检查点、重执行、进程恢复、局部弹性、检测和恢复失败回退。明确运行时钟与日历时钟、恢复到服务与硬件维修的区别。

优先复现专家锁定版本根目录 `正确有效产出改进分析.html` 的 V4 基线与关键机制组合，再通过通用结构和参数适配运行。参考其场景、仿真和 Shapley 源模块，避免以另一目录的最新审核结果替代指定基准。新增模型假设单独标记，不能把改进版本与专家基线的差异全部计为机制收益。

后续工具沿同一契约补齐：

| 工具 | 首批支持范围与作用 |
|---|---|
| RBD | 串并联及 k-out-of-n 的有界结构，展示成功条件并计算适用静态子模型 |
| FTA＋BDD | AND/OR 故障树、重复基本事件的一致引用和布尔求解；相关性需显式建模，不默认独立 |
| CTMC | 有限状态故障与恢复、瞬态/稳态结果；指数等待时间和状态规模限制显式声明 |
| 离散事件仿真 | 训练进度、非指数延迟、降级、回退、污染和恢复过程，是主指标的首期求解内核 |

不同方法的对比必须采用相同语义和适用假设。静态图、状态模型与动态仿真可以协作，不强制互相转换所有细节。界面只把通过基准验证的能力标记为可用。

每个方法有规模限制和超限反馈。仿真使用同质组件/故障域聚合，避免把每张卡每个训练 step 都展开。方案搜索与仿真记录计算预算、样本数、停止条件和未覆盖空间；正式候选使用独立复核样本，减少在同一批随机样本上选择最优带来的偏差。

## 8. 文件输入、模板与方法沉淀

首批建议覆盖 JSON、CSV、XLSX、Markdown、PDF、PNG/JPEG 架构图；保留解析器注册接口。模板优先形成架构资产、故障模式、机制、参数证据四类表。

处理链为：导入/监听变化 → 输入快照 → 格式解析和候选结构 → 来源定位及歧义 → 关键项确认 → schema/单位/引用/语义校验 → 已确认模型版本。

图片和非结构化文档的解析依赖配置的多模态或文本模型；无法可靠识别时显示待确认项，允许表格或图上修正，不编造连接关系与参数。原型必须提供真实解析路径及人工修正入口，不能只提供演示数据导入。

文件监听在用户授权的目录内启用。变化触发差异展示与旧结果失效标记，正在运行的实验继续使用原快照；确认后再启动新实验。

真实数据在用户部署环境中处理。外网演示使用合成或公开样例，内网通过配置模型端点接入真实材料；送入模型的内容受部署策略约束。“本地文件解析”不自动等于“内容未发往模型服务”。

成功工作流可以导出候选 Skill、解析模板或工具包装；附输入输出契约、示例、校验及版本，经验证后发布为可复用资产。

## 9. LUI 和 Agent 交互

- 左侧：项目、Agent、Skill、Tool、故障模式库、机制库、参数证据库、模型/场景库、验证案例、事件台账、实验与报告；显示来源、版本、连接状态及配置。库界面支持检索、维护、导入导出和引用关系查看。
- 中间：当前步骤、目标与分解树、架构图/RBD/FTA、参数表、求解状态、风险与损失、方案比较及验证结果。
- 右侧或底部：OpenCode 会话，可加载工作流、解释推荐、回应缺失信息和调整方案。
- 中间资产与对话中的引用互相定位；图上的组件、故障和机制对应同一模型对象，能够影响计算。
- 每个结果可展开到参数、假设、输入文件位置、工具运行及验证证据。

长任务提供状态、进度、取消和失败信息。取消保留最近完整结果；未完成样本与正式结果分开。原型支持从最近完整步骤继续，仿真中断可从记录的配置和种子重跑；任意时刻的仿真进程检查点恢复不作为首批承诺。

## 10. 验证与可信性

验证分四层：数据/语义校验、求解实现检查、方法交叉校验、现实符合性验证。

首批必须通过的检查：

1. 单位、引用、概率范围、恢复前置条件和参数来源完整性。
2. 无故障、零开销、不可恢复、完全检测与完全漏检等有意义的边界场景。
3. 正确产出与互斥损失的守恒、重复事件引用一致性、机制开销与失败回退不遗漏。
4. 已知解析解与受限等价模型的求解对照；专家基线和关键组合回归。
5. 相同模型、版本、配置及种子可重现；输入变化不污染旧结果。
6. 目标上界检查：例如 300 秒计算/4 秒阻塞保存的长期无故障产出约为 98.684%，不能直接宣称满足 99% 目标。这是另一审核分支的条件化测试样例，不是指定根目录 HTML 的默认配置；后者保存的基线为 intervalSeconds=7200、saveSeconds=10，周期语义按其引擎复现。
7. 近阈值结果显示采样精度及“证据不足以稳定判断”，不把均值点估计刚越线包装成有统计保证的结论。
8. 每次报告清楚区分合成验证、参考模型复现、真实台账校准和留出数据预测验证。
9. 交付口径回归：同一轨迹在期末未恢复污染时 `delivery=0`，而 `effective` 可能大于零；期末已恢复时按正确净进度计分。不能用“保留最后干净检查点”策略的结果替代严格交付规则。
10. 资产库引用、覆盖和版本隔离：故障模式与机制多对多关系有效，参数证据匹配适用条件，库升级不改写已有实验快照。

实测条件不足时，原型仍应完整支持台账导入、确定性事件回放与验证报告；真实预测准确度需由用户环境的数据检验，不能预先承诺。所谓超过业界水平，以可复现对标案例的误差、覆盖、稳健性、性能与工程效率证明。

## 11. 原型交付范围与能力顺序

| 阶段 | 交付结果 | 验收重点 |
|---|---|---|
| 共同契约与基准 | 指标字典、目标表、场景 schema、证据结构和专家参考快照 | 语义一致，原始与示例参数区分，基线可复现 |
| 训练闭环 | 分配策略、仿真、机制对比、目标搜索、损失解释和验证 | 从产品目标得到具体设计要求，回算达标并可追溯 |
| 交互原型 | OpenCode、Skill、MCP、真实文件解析、资产库维护、LUI 和报告 | 从库资产选用/维护与导入到交付可交互完成，过程资产可查看和导出 |
| 方法与通用性验证 | 有界 RBD/FTA/BDD/CTMC、一个非训练最小案例 | 替换场景和方法无需修改通用工作流或界面核心 |
| 持续演进 | 方法研究记录、运行质量与用户反馈、版本评测 | 更新候选经回归后发布，不自动替换已验证计算逻辑 |

阶段之间能独立开发的部分可重叠推进，不表示需要额外 Agent。原型最终包含上述通用性验证；首个可演示闭环优先交付训练场景。

首期不包含多作业调度优化、全产品生产级模型、3D 数字孪生、企业多人权限体系和任意模型自动形式化验证。接口保留扩展空间，避免将其误标为已支持。

## 12. 最终报告与持续演进

报告包含目标与结论、系统与工作负载、模型和假设、输入证据、分配方案、达标差距、推荐及替代方案、收益和开销、敏感性与不确定性、验证结果、限制及详细资产索引。原型优先输出 Markdown、可交互 HTML 和机器可读 JSON 资产包。

反馈区分用户接受、修改、拒绝及原因；任务指标包括有效完成率、工具失败率、人工修正量、模型校验通过率和复现情况。接受率不能代替数值正确性或现实有效性。

定期研究 Agent、Skill、MCP 和可靠性方法，输出有来源的改进建议，经过基准与回归验证后更新。具体研究频率及调度在实施配置中决定；本文不创建定时任务。
